<div class="erklaert">
<div class="tldr">
<p>Beim <strong>Messaging</strong> schicken Dienste einander keine Aufrufe, sondern <strong>Nachrichten</strong> über einen <strong>Vermittler</strong> (Broker). Der Absender legt eine Nachricht ab und arbeitet weiter; der Empfänger holt sie, wann er kann. Fällt der Empfänger aus oder ist überlastet, warten die Nachrichten – nichts geht verloren, und der Absender merkt nichts davon.</p>
<p>Es gibt zwei grundverschiedene Modelle. In einer <strong>Warteschlange</strong> (RabbitMQ, JMS, Amazon SQS) bekommt jede Nachricht genau ein Empfänger, danach ist sie weg – ideal, um Arbeit zu verteilen. In einem <strong>Log</strong> (Apache Kafka) bleiben Nachrichten gespeichert, jeder Leser merkt sich nur seine Position und kann jederzeit zurückspulen – ideal, wenn viele unabhängige Systeme denselben Strom von Ereignissen brauchen.</p>
</div>

<p>Ein Log ist im Grunde die einfachste denkbare Datenstruktur: eine Datei, an die nur hinten angehängt wird. Genau deshalb ist es so schnell – Schreiben und Lesen sind fast immer sequenziell, und das Betriebssystem bedient die meisten Leser aus seinem <a href="/it-konzepte/dateisystem/">Seitencache</a>. Kafka schafft so auf gewöhnlicher Hardware Hunderttausende Nachrichten pro Sekunde und Rechner.</p>

<h2 id="kafka">Kafka: Topics, Partitionen, Gruppen</h2>
<p>Ein einzelnes Log hätte eine Grenze: Es liegt auf einem Rechner und wird von einem Leser pro Gruppe gelesen. Kafka teilt deshalb jedes <strong>Topic</strong> in <strong>Partitionen</strong> – mehrere unabhängige Logs. Jede Nachricht hat einen <strong>Schlüssel</strong>, etwa die Kunden-ID, und der Schlüssel bestimmt per Hash die Partition. In einer <strong>Consumer Group</strong> bekommt jeder Leser eigene Partitionen zugeteilt:</p>

<p>Daraus folgen die zwei Regeln, die man über Kafka wissen muss:</p>
<ul>
  <li><strong>Reihenfolge gibt es nur innerhalb einer Partition.</strong> Alle Ereignisse eines Kunden landen über den Schlüssel in derselben Partition und werden in Reihenfolge gelesen. Über Partitionen hinweg gibt es keine Reihenfolge. Wer „Bestellung angelegt“ und „Bestellung storniert“ mit verschiedenen Schlüsseln schickt, kann sie in falscher Reihenfolge bekommen.</li>
  <li><strong>Die Zahl der Partitionen begrenzt die Parallelität.</strong> Mehr Leser als Partitionen bringt nichts – die überzähligen sitzen untätig herum. Partitionen später zu erhöhen, ändert die Zuordnung der Schlüssel; deshalb plant man sie großzügig.</li>
</ul>
<p>Jede Partition wird außerdem auf mehrere Rechner kopiert. Ein Rechner ist Anführer der Partition, die anderen folgen – das Muster aus dem Eintrag zu <a href="/it-konzepte/verteilte-systeme/">verteilten Systemen</a>. Seit Version 4.0 verwaltet Kafka das mit einem eigenen Raft-basierten Verfahren (KRaft) statt mit dem früher nötigen ZooKeeper.</p>

<h2 id="absturz">Wenn ein Leser abstürzt</h2>
<p>Ein Leser holt eine Nachricht, verarbeitet sie und meldet dann dem Vermittler „erledigt“ – bei Kafka, indem er seinen Offset weiterschreibt (<em>commit</em>). Was passiert, wenn er zwischen diesen Schritten abstürzt? Die Antwort hängt an der Reihenfolge:</p>

<p>„Erst verarbeiten, dann bestätigen“ ist der übliche Weg: Nichts geht verloren, dafür kann eine Nachricht doppelt kommen – <strong>at least once</strong>. Also müssen Empfänger mit Doppelten umgehen können, genau wie im Eintrag zu <a href="/it-konzepte/verteilte-systeme/">verteilten Systemen</a> beschrieben: idempotente Operationen oder eine Tabelle bereits verarbeiteter Nachrichten-IDs.</p>
<h3>Giftnachrichten</h3>
<p>Eine Nachricht, die der Empfänger nie verarbeiten kann – kaputtes JSON, ein Wert, den der Code nicht erwartet –, ist eine <strong>Giftnachricht</strong>. Weil der Empfänger sie nie bestätigt, bekommt er sie wieder und wieder, und in Kafka blockiert sie dabei die ganze Partition: Alles dahinter wartet. Die Lösung ist eine <strong>Dead Letter Queue</strong>: Nach einigen gescheiterten Versuchen wird die Nachricht in ein eigenes Topic verschoben, der Strom läuft weiter, und ein Mensch schaut sich den Fall später an.</p>

<span class="c">// Empfangen: eine Methode, Spring kümmert sich um Gruppe, Partitionen und Offsets</span>
@KafkaListener(topics = <span class="s">"bestellungen"</span>, groupId = <span class="s">"versand"</span>)
<span class="k">void</span> beiBestellung(BestellungAufgegeben e) {
    <span class="k">if</span> (verarbeitet.existsById(e.bestellId())) <span class="k">return</span>;   <span class="c">// Doppelte ignorieren</span>
    versand.planen(e);
}

<span class="c">// Nach 3 gescheiterten Versuchen in die Dead Letter Queue ("bestellungen.DLT")</span>
@Bean
DefaultErrorHandler fehlerbehandlung(KafkaTemplate&lt;Object, Object&gt; t) {
    <span class="k">return new</span> DefaultErrorHandler(<span class="k">new</span> DeadLetterPublishingRecoverer(t), <span class="k">new</span> FixedBackOff(<span class="s">1000</span>, <span class="s">2</span>));
}</code></pre>

<h2 id="irrtuemer">Häufige Irrtümer</h2>
<div class="myth">
  <div><b>„Kafka ist eine Warteschlange.“</b> – Kafka ist ein Log. Nachrichten verschwinden nicht beim Lesen, und mehrere Gruppen lesen alles. Für klassische Aufgabenverteilung mit Prioritäten oder Einzelbestätigung sind Warteschlangen oft die bessere Wahl.</div>
  <div><b>„Nachrichten kommen in der Reihenfolge an, in der sie gesendet wurden.“</b> – Nur innerhalb einer Partition. Was zusammen in Reihenfolge bleiben muss, braucht denselben Schlüssel.</div>
  <div><b>„Mehr Leser, mehr Durchsatz.“</b> – Nur bis zur Zahl der Partitionen. Danach warten die zusätzlichen Leser untätig.</div>
  <div><b>„Jede Nachricht wird genau einmal verarbeitet.“</b> – Kafka kann innerhalb seiner selbst mit Transaktionen „exactly once“ herstellen. Sobald die Verarbeitung eine Datenbank oder eine externe API berührt, muss der Empfänger Doppelte selbst erkennen.</div>
  <div><b>„Asynchron heißt: Fehler sind nicht mehr mein Problem.“</b> – Sie tauchen nur später und woanders auf. Ohne Dead Letter Queue, Überwachung der Rückstände (consumer lag) und Alarme bleiben sie unbemerkt.</div>
