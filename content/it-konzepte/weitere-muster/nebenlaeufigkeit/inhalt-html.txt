<p>Sobald mehrere Threads gleichzeitig arbeiten, entstehen neue Arten von Fehlern: verlorene Änderungen, Deadlocks, Threads, die ewig warten. Sie treten nur manchmal auf und sind schwer zu finden. Die Muster dieser Gruppe sind bewährte Wege, Nebenläufigkeit beherrschbar zu machen. Sie stammen großteils aus <em>Pattern-Oriented Software Architecture, Band 2</em> (2000) und aus Doug Leas <em>Concurrent Programming in Java</em>.</p>
<p>Alle Beispiele nutzen Java 21, wo es passt mit <strong>virtuellen Threads</strong>. Weil nebenläufige Programme bei jedem Lauf etwas anders ablaufen, geben die Beispiele vor allem Ergebnisse und Zählerstände aus, die immer gleich sind, keine Zwischenstände. Gemessene Zeiten sind gerundet.</p>

<h3>Die Idee</h3>
<p>Wer Arbeit <strong>erzeugt</strong> und wer sie <strong>erledigt</strong>, wird durch eine Warteschlange getrennt. Erzeuger legen Aufgaben hinein, Verbraucher nehmen sie heraus. Ist die Schlange <strong>voll</strong>, warten die Erzeuger. Ist sie <strong>leer</strong>, warten die Verbraucher. So passen sich beide Seiten automatisch aneinander an, ohne voneinander zu wissen. Es ist das Messaging-Prinzip der Enterprise Integration Patterns, nur innerhalb eines Programms.</p>
<h3>Im Code</h3>
<p>Eine <code>ArrayBlockingQueue</code> mit fünf Plätzen verbindet zwei schnelle Erzeuger mit drei langsameren Verbrauchern, alle als virtuelle Threads. <code>put()</code> blockiert bei voller, <code>take()</code> bei leerer Schlange. Am Ende bekommt jeder Verbraucher eine „Giftpille“, ein besonderes Objekt, das ihm sagt, dass keine Arbeit mehr kommt.</p>
<details class="code"><summary>Java-21-Code: ProducerConsumer.java</summary><p>Direkt ausführbar mit <code>java ProducerConsumer.java</code></p><pre><code class="language-java">// Producer-Consumer
// Erzeuger und Verbraucher sind über eine Warteschlange entkoppelt und arbeiten in ihrem eigenen Tempo.
// Start: java ProducerConsumer.java

import java.util.Map;
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicInteger;

public class ProducerConsumer {

    record Bestellung(String quelle, int nr) {}
    static final Bestellung ENDE = new Bestellung(&quot;ENDE&quot;, -1);         // &quot;Giftpille&quot;: signalisiert das Ende

    public static void main(String[] args) throws Exception {
        BlockingQueue&lt;Bestellung&gt; warteschlange = new ArrayBlockingQueue&lt;&gt;(5);   // begrenzt: höchstens 5
        AtomicInteger maxFuellstand = new AtomicInteger();
        Map&lt;String, Integer&gt; verarbeitet = new ConcurrentHashMap&lt;&gt;();
        int verbraucher = 3;

        try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
            // --- Erzeuger: Shop und App liefern je 10 Bestellungen, schnell ---
            for (String quelle : new String[] { &quot;Shop&quot;, &quot;App&quot; }) {
                ex.submit(() -&gt; {
                    for (int i = 1; i &lt;= 10; i++) {
                        warteschlange.put(new Bestellung(quelle, i));      // blockiert, wenn die Schlange voll ist
                        maxFuellstand.accumulateAndGet(warteschlange.size(), Math::max);
                        Thread.sleep(5);
                    }
                    return null;
                });
            }
            // --- Verbraucher: drei Lager-Worker, langsamer ---
            for (int w = 1; w &lt;= verbraucher; w++) {
                String name = &quot;Worker &quot; + w;
                ex.submit(() -&gt; {
                    while (true) {
                        Bestellung b = warteschlange.take();             // blockiert, wenn die Schlange leer ist
                        if (b == ENDE) return null;
                        Thread.sleep(30);                                // Verarbeitung dauert
                        verarbeitet.merge(b.quelle(), 1, Integer::sum);
                    }
                });
            }
            // --- Ende signalisieren, sobald alle Erzeuger fertig sind ---
            ex.submit(() -&gt; {
                while (verarbeitet.values().stream().mapToInt(Integer::intValue).sum() + warteschlange.size() &lt; 20) Thread.sleep(10);
                for (int i = 0; i &lt; verbraucher; i++) warteschlange.put(ENDE);
                return null;
            });
        }

        System.out.println(&quot;Verarbeitet:          &quot; + new java.util.TreeMap&lt;&gt;(verarbeitet));
        System.out.println(&quot;Größter Füllstand:    &quot; + Math.min(maxFuellstand.get(), 5) + &quot; (Kapazität 5)&quot;);
        System.out.println(&quot;Erzeuger haben gewartet, wenn die Schlange voll war, statt den Speicher zu fluten.&quot;);
    }
}</code></pre><p><strong>Ausgabe</strong></p><pre><code>Verarbeitet:          {App=10, Shop=10}
Größter Füllstand:    5 (Kapazität 5)
Erzeuger haben gewartet, wenn die Schlange voll war, statt den Speicher zu fluten.</code></pre></details>
<h3>Worauf achten</h3>
<p>Die Warteschlange sollte <strong>begrenzt</strong> sein. Eine unbegrenzte Schlange nimmt alles an, bis der Speicher voll ist, wenn die Verbraucher dauerhaft langsamer sind. Die Begrenzung bremst die Erzeuger aus, man spricht von <em>Backpressure</em>. Für das saubere Beenden gibt es zwei übliche Wege: eine Giftpille pro Verbraucher wie im Beispiel oder das Unterbrechen der Verbraucher-Threads. Und wie bei Competing Consumers gilt: Mit mehreren Verbrauchern ist die Reihenfolge der Verarbeitung nicht garantiert.</p>
<h3>In der Praxis</h3>
<p><code>BlockingQueue</code> mit ihren Implementierungen <code>ArrayBlockingQueue</code>, <code>LinkedBlockingQueue</code> und <code>SynchronousQueue</code>. Jeder <code>ExecutorService</code> hat intern eine Warteschlange. Die LMAX Disruptor-Bibliothek ist eine extrem schnelle Variante. Über Prozessgrenzen hinweg übernehmen Message Broker diese Rolle.</p>

<h3>Die Idee</h3>
<p>Statt für jede Aufgabe einen neuen Thread zu starten, gibt es eine <strong>feste Zahl von Threads</strong>, die eine Warteschlange von Aufgaben abarbeiten. Ist ein Thread fertig, nimmt er sich die nächste Aufgabe. Threads werden so wiederverwendet, und ihre Zahl ist nach oben begrenzt. Der Thread Pool ist eine Kombination aus <em>Object Pool</em> (Gruppe 1) und <em>Producer-Consumer</em> (Muster 36).</p>
<h3>Im Code</h3>
<p>Ein <code>Executors.newFixedThreadPool(4)</code> erledigt zwölf Aufgaben à 100 ms. Es werden genau vier Threads benutzt, und es dauert drei Runden, also etwa 300 ms. Im zweiten Teil laufen 10.000 wartende Aufgaben mit virtuellen Threads, je einem pro Aufgabe, in deutlich unter einer Sekunde.</p>
<details class="code"><summary>Java-21-Code: ThreadPool.java</summary><p>Direkt ausführbar mit <code>java ThreadPool.java</code></p><pre><code class="language-java">// Thread Pool
// Eine feste Anzahl von Threads arbeitet eine Warteschlange von Aufgaben ab.
// Start: java ThreadPool.java

import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class ThreadPool {

    static long ms(long start) { return Math.round((System.nanoTime() - start) / 1e8) * 100; }

    public static void main(String[] args) throws Exception {
        // --- 1. Klassischer Thread Pool: 4 Plattform-Threads für 12 Aufgaben ---
        Set&lt;String&gt; benutzteThreads = ConcurrentHashMap.newKeySet();
        long start = System.nanoTime();
        ExecutorService pool = Executors.newFixedThreadPool(4);
        for (int i = 1; i &lt;= 12; i++) {
            pool.submit(() -&gt; {
                benutzteThreads.add(Thread.currentThread().getName());
                Thread.sleep(100);                                   // z. B. Rechnung als PDF erzeugen
                return null;
            });
        }
        pool.shutdown();                                             // keine neuen Aufgaben mehr annehmen
        pool.awaitTermination(10, TimeUnit.SECONDS);                 // auf die laufenden warten
        System.out.println(&quot;Fester Pool: 12 Aufgaben à 100 ms mit 4 Threads&quot;);
        System.out.println(&quot;  verschiedene Threads benutzt: &quot; + benutzteThreads.size());
        System.out.println(&quot;  Dauer ca. &quot; + ms(start) + &quot; ms  (3 Runden à 4 Aufgaben)&quot;);

        // --- 2. Java 21: virtuelle Threads, ein Thread pro Aufgabe, kein Pool nötig ---
        start = System.nanoTime();
        try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i &lt; 10_000; i++) {
                ex.submit(() -&gt; { Thread.sleep(100); return null; }); // wartende Aufgaben, z. B. auf eine Antwort
            }
        }
        System.out.println(&quot;\nVirtuelle Threads: 10.000 wartende Aufgaben à 100 ms&quot;);
        System.out.println(&quot;  Dauer deutlich unter 1 Sekunde: &quot; + (ms(start) &lt; 1_000));
    }
}</code></pre><p><strong>Ausgabe</strong></p><pre><code>Fester Pool: 12 Aufgaben à 100 ms mit 4 Threads
  verschiedene Threads benutzt: 4
  Dauer ca. 300 ms  (3 Runden à 4 Aufgaben)

Virtuelle Threads: 10.000 wartende Aufgaben à 100 ms
  Dauer deutlich unter 1 Sekunde: true</code></pre></details>
<h3>Worauf achten</h3>
<p>Die richtige <strong>Poolgröße</strong> hängt von der Art der Arbeit ab: Für rechenintensive Aufgaben etwa so viele Threads wie Prozessorkerne, mehr bringen nichts. Für Aufgaben, die überwiegend <strong>warten</strong> (Datenbank, Netzwerk, Dateien), waren früher große Pools nötig. Seit <strong>Java 21</strong> sind dafür virtuelle Threads die bessere Wahl: Sie sind so billig, dass man sie nicht mehr poolen muss, Millionen gleichzeitig sind möglich. Plattform-Thread-Pools bleiben sinnvoll für rechenintensive Arbeit und um die Last auf eine Ressource bewusst zu begrenzen. Pools müssen immer mit <code>shutdown()</code> beendet werden, sonst läuft das Programm nicht zu Ende. Die try-with-resources-Form von <code>ExecutorService</code> nimmt einem das seit Java 19 ab.</p>
<h3>In der Praxis</h3>
<p><code>ExecutorService</code> mit <code>newFixedThreadPool</code>, <code>newCachedThreadPool</code>, <code>ForkJoinPool</code> (für Streams mit <code>parallel()</code>), Thread-Pools in Webservern wie Tomcat, die seit Spring Boot 3.2 per Einstellung durch virtuelle Threads ersetzt werden können.</p>

<h3>Die Idee</h3>
<p>Ein Future ist ein <strong>Platzhalter für ein Ergebnis, das es noch nicht gibt</strong>. Wer eine langwierige Aufgabe startet, bekommt sofort ein Future zurück und kann weiterarbeiten. Später kann er auf das Ergebnis warten, oder er hängt gleich <strong>Folgeschritte</strong> an, die automatisch laufen, sobald das Ergebnis da ist. „Promise“ bezeichnet die Seite, die das Ergebnis später einlöst. In Java vereint <code>CompletableFuture</code> beides.</p>
<h3>Im Code</h3>
<p>Eine Produktseite braucht Preis, Bestand und Versandkosten von drei langsamen Diensten. Nacheinander abgefragt dauert das etwa 900 ms, als drei Futures parallel etwa 300 ms. <code>thenCombine</code> setzt die Ergebnisse zusammen, <code>thenApply</code> verarbeitet weiter, <code>exceptionally</code> liefert bei einem Fehler einen Ersatzwert, und <code>completeOnTimeout</code> begrenzt die Wartezeit.</p>
<details class="code"><summary>Java-21-Code: FuturePromise.java</summary><p>Direkt ausführbar mit <code>java FuturePromise.java</code></p><pre><code class="language-java">// Future / Promise

// Start: java FuturePromise.java

import java.util.Locale;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class FuturePromise {

    static void warte(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) { throw new RuntimeException(e); } }
    static long ms(long start) { return Math.round((System.nanoTime() - start) / 1e8) * 100; }

    static int bestand(String artikel)    { warte(300); return 7; }
    static long versandCent(String plz)   { warte(300); return 490; }
    static long empfehlungen()            { warte(200); throw new IllegalStateException(&quot;Empfehlungsdienst nicht erreichbar&quot;); }

        var ex = Executors.newVirtualThreadPerTaskExecutor();

        // --- Nacheinander: die Zeiten addieren sich ---
        long start = System.nanoTime();
        var seq = new Produktseite(preisCent(&quot;Lampe&quot;), bestand(&quot;Lampe&quot;), versandCent(&quot;20457&quot;));
        System.out.println(&quot;Nacheinander: &quot; + seq + &quot;, Dauer ca. &quot; + ms(start) + &quot; ms&quot;);

        start = System.nanoTime();

        CompletableFuture&lt;Integer&gt; lager = CompletableFuture.supplyAsync(() -&gt; bestand(&quot;Lampe&quot;), ex);
        CompletableFuture&lt;Long&gt; versand = CompletableFuture.supplyAsync(() -&gt; versandCent(&quot;20457&quot;), ex);

        CompletableFuture&lt;Produktseite&gt; seite = preis.thenCombine(lager, (p, b) -&gt; new long[] { p, b })
                .thenCombine(versand, (pb, v) -&gt; new Produktseite(pb[0], (int) pb[1], v));
        System.out.println(&quot;Parallel:     &quot; + seite.join() + &quot;, Dauer ca. &quot; + ms(start) + &quot; ms&quot;);

        System.out.println(&quot;Weiterverarbeitet: &quot; + text);

        String empf = CompletableFuture.supplyAsync(FuturePromise::empfehlungen, ex)
                .thenApply(n -&gt; n + &quot; Empfehlungen&quot;)
                .exceptionally(fehler -&gt; &quot;keine Empfehlungen (&quot; + fehler.getCause().getMessage() + &quot;)&quot;)
                .join();
        System.out.println(&quot;Mit Fehler:   &quot; + empf);

        String mitLimit = CompletableFuture.supplyAsync(() -&gt; { warte(2_000); return &quot;zu spät&quot;; }, ex)
                .completeOnTimeout(&quot;Standardwert nach 500 ms&quot;, 500, TimeUnit.MILLISECONDS)

        System.out.println(&quot;Mit Zeitlimit: &quot; + mitLimit);

<p>Ein blockierendes <code>get()</code> oder <code>join()</code> zu früh im Code macht den Vorteil zunichte. <h3>Die Idee</h3>
<p>Ein Active Object hat einen <strong>eigenen Thread</strong>. Ruft jemand eine seiner Methoden auf, wird die Arbeit nicht sofort im Thread des Aufrufers erledigt, sondern als Auftrag in eine <strong>Warteschlange</strong> gestellt. Der Aufrufer bekommt sofort ein Future zurück. Der Thread des Objekts arbeitet die Aufträge nacheinander ab. Weil nur dieser eine Thread den Zustand des Objekts berührt, sind <strong>keine Sperren</strong> nötig.</p>
<h3>Im Code</h3>
<p>Das <code>Lager</code> hat einen <code>SingleThreadExecutor</code> als eigenen Thread und Warteschlange. Seine öffentlichen Methoden verpacken den Auftrag und reihen ihn ein. 1.000 virtuelle Threads entnehmen gleichzeitig Bücher und liefern Tassen. Am Ende stimmt der Bestand exakt, obwohl die interne <code>HashMap</code> nicht threadsicher ist und kein einziges <code>synchronized</code> im Code steht.</p>
<details class="code"><summary>Java-21-Code: ActiveObject.java</summary><p>Direkt ausführbar mit <code>java ActiveObject.java</code></p><pre><code class="language-java">// Active Object
// Methodenaufrufe werden nicht sofort ausgeführt, sondern in eine Warteschlange gestellt
// und von einem eigenen Thread des Objekts nacheinander abgearbeitet.
// Start: java ActiveObject.java

import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.function.Supplier;

public class ActiveObject {

    // --- Das Active Object: eigener Thread, eigener Zustand, keine Sperren nötig ---
    static final class Lager implements AutoCloseable {
        private final ExecutorService eigenerThread = Executors.newSingleThreadExecutor();   // Scheduler + Queue
        private final Map&lt;String, Integer&gt; bestand = new HashMap&lt;&gt;();                       // nur dieser Thread greift zu
        private int auftraege = 0;

        // Öffentliche Methoden: nehmen den Auftrag an und kehren sofort zurück (Proxy)
        CompletableFuture&lt;Void&gt; liefere(String artikel, int menge) {
            return einreihen(() -&gt; { bestand.merge(artikel, menge, Integer::sum); auftraege++; return null; });
        }
        CompletableFuture&lt;Boolean&gt; entnehme(String artikel, int menge) {
            return einreihen(() -&gt; {
                auftraege++;
                int da = bestand.getOrDefault(artikel, 0);
                if (da &lt; menge) return false;
                bestand.put(artikel, da - menge);
                return true;
            });
        }
        CompletableFuture&lt;String&gt; bericht() {
            return einreihen(() -&gt; &quot;Bestand &quot; + new java.util.TreeMap&lt;&gt;(bestand) + &quot; nach &quot; + auftraege + &quot; Aufträgen&quot;);
        }

        private &lt;T&gt; CompletableFuture&lt;T&gt; einreihen(Supplier&lt;T&gt; auftrag) {
            return CompletableFuture.supplyAsync(auftrag, eigenerThread);   // Method Request in die Warteschlange
        }
        public void close() { eigenerThread.shutdown(); }
    }

    public static void main(String[] args) {
        try (Lager lager = new Lager();
             var aufrufer = Executors.newVirtualThreadPerTaskExecutor()) {

            lager.liefere(&quot;Buch&quot;, 1_000).join();

            // 1.000 Aufrufer gleichzeitig, jeder entnimmt 1 Buch und liefert 1 Tasse
            var erfolge = new java.util.concurrent.atomic.AtomicInteger();
            var futures = new java.util.ArrayList&lt;CompletableFuture&lt;?&gt;&gt;();
            for (int i = 0; i &lt; 1_000; i++) {
                futures.add(CompletableFuture.runAsync(() -&gt; {
                    if (lager.entnehme(&quot;Buch&quot;, 1).join()) erfolge.incrementAndGet();
                    lager.liefere(&quot;Tasse&quot;, 1).join();
                }, aufrufer));
            }
            futures.forEach(CompletableFuture::join);

            System.out.println(&quot;Erfolgreiche Entnahmen: &quot; + erfolge.get());
            System.out.println(lager.bericht().join());
            System.out.println(&quot;Keine einzige Sperre im Code: der Zustand gehört genau einem Thread.&quot;);
        }
    }
}</code></pre><p><strong>Ausgabe</strong></p><pre><code>Erfolgreiche Entnahmen: 1000

<h3>Worauf achten</h3>
<p>Das Muster tauscht Sperren gegen <strong>Serialisierung</strong>: Alle Aufträge laufen nacheinander. Bei sehr vielen Aufrufen wird der eine Thread zum Engpass. Dauert ein Auftrag lange, warten alle anderen. Und ruft das Active Object aus einem Auftrag heraus blockierend sich selbst auf, wartet es auf sich selbst, ein Deadlock. Das GoF-nahe Original von Douglas Schmidt (POSA 2) unterscheidet die Rollen Proxy, Method Request, Activation List, Scheduler, Servant und Future. Im Beispiel übernimmt der <code>ExecutorService</code> mehrere davon.</p>

<h3>Die Idee</h3>
<p>Ein Monitor Object <strong>schützt seinen Zustand selbst</strong>: Alle seine Methoden sind so gesichert, dass immer nur ein Thread gleichzeitig darin arbeiten kann. Andere Threads warten, bis er fertig ist. Der Aufrufer muss sich um nichts kümmern. Zusätzlich kann ein Monitor <em>Bedingungen</em> bieten, auf die Threads warten können, siehe Guarded Suspension (Muster 43). Das Konzept stammt von Tony Hoare und Per Brinch Hansen aus den 1970ern.</p>
<h3>Im Code</h3>
<p>Ein ungeschützter Zähler, von acht Threads je 200.000-mal erhöht, verliert Änderungen, weil <code>wert++</code> aus drei Schritten besteht: lesen, erhöhen, schreiben. Mit <code>synchronized</code> stimmt das Ergebnis. Das <code>Konto</code> nutzt eine <code>ReentrantLock</code> und prüft und ändert den Saldo als eine geschützte Einheit. 5.000 gleichzeitige Abbuchungen von 1 € auf ein Konto mit 1.000 € ergeben genau 1.000 erfolgreiche, und der Saldo wird nie negativ.</p>
<details class="code"><summary>Java-21-Code: MonitorObject.java</summary><p>Direkt ausführbar mit <code>java MonitorObject.java</code></p><pre><code class="language-java">// Monitor Object
// Ein Objekt schützt seinen Zustand selbst: Es lässt immer nur einen Thread gleichzeitig in seine Methoden.
// Start: java MonitorObject.java

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class MonitorObject {

    // --- Ungeschützt: mehrere Threads können sich gegenseitig Änderungen überschreiben ---
    static final class Zaehler {
        private long wert;
        void erhoehe() { wert++; }                       // lesen, +1, schreiben: drei Schritte, nicht atomar
        long wert()    { return wert; }
    }

    // --- Monitor mit synchronized: Java-Objekte haben einen eingebauten Monitor ---
    static final class SicherZaehler {
        private long wert;
        synchronized void erhoehe() { wert++; }
        synchronized long wert()    { return wert; }
    }

    // --- Monitor mit ReentrantLock: mehr Kontrolle, gut für virtuelle Threads ---
    static final class Konto {
        private final ReentrantLock sperre = new ReentrantLock();
        private long saldoCent;

        boolean abbuchen(long cent) {
            sperre.lock();
            try {
                if (saldoCent &lt; cent) return false;      // Prüfen und Ändern als EINE geschützte Einheit
                saldoCent -= cent;
                return true;
            } finally {
                sperre.unlock();
            }
        }
        void einzahlen(long cent) { sperre.lock(); try { saldoCent += cent; } finally { sperre.unlock(); } }
        long saldo()              { sperre.lock(); try { return saldoCent; } finally { sperre.unlock(); } }
    }

    static void parallel(int threads, int jeThread, Runnable r) throws InterruptedException {
        ExecutorService ex = Executors.newFixedThreadPool(threads);
        for (int t = 0; t &lt; threads; t++) ex.submit(() -&gt; { for (int i = 0; i &lt; jeThread; i++) r.run(); });
        ex.shutdown();
        ex.awaitTermination(30, TimeUnit.SECONDS);
    }

    public static void main(String[] args) throws Exception {
        Zaehler unsicher = new Zaehler();
        SicherZaehler sicher = new SicherZaehler();
        parallel(8, 200_000, unsicher::erhoehe);
        parallel(8, 200_000, sicher::erhoehe);
        System.out.println(&quot;8 Threads erhöhen je 200.000-mal, erwartet 1.600.000:&quot;);
        System.out.println(&quot;  ohne Schutz:        &quot; + (unsicher.wert() == 1_600_000 ? &quot;zufällig korrekt&quot; : &quot;Änderungen verloren gegangen&quot;));
        System.out.println(&quot;  mit synchronized:   &quot; + sicher.wert());

        Konto konto = new Konto();
        konto.einzahlen(100_000);                        // 1.000 €
        var erfolge = new java.util.concurrent.atomic.AtomicInteger();
        try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i &lt; 5_000; i++) ex.submit(() -&gt; { if (konto.abbuchen(100)) erfolge.incrementAndGet(); });
        }
        System.out.println(&quot;\n5.000 gleichzeitige Abbuchungen à 1 € von 1.000 €:&quot;);
        System.out.println(&quot;  erfolgreich: &quot; + erfolge.get() + &quot;, Saldo: &quot; + konto.saldo() + &quot; Cent (nie negativ)&quot;);
    }
}</code></pre><p><strong>Ausgabe</strong></p><pre><code>8 Threads erhöhen je 200.000-mal, erwartet 1.600.000:
  ohne Schutz:        Änderungen verloren gegangen
  mit synchronized:   1600000

5.000 gleichzeitige Abbuchungen à 1 € von 1.000 €:
  erfolgreich: 1000, Saldo: 0 Cent (nie negativ)</code></pre></details>
<h3>Worauf achten</h3>
<p>Jedes Java-Objekt hat einen eingebauten Monitor, den <code>synchronized</code> verwendet. Wichtig ist, <strong>zusammengehörige Schritte gemeinsam</strong> zu schützen: Getrennte, je für sich synchronisierte Methoden <code>pruefe()</code> und <code>buche()</code> helfen nicht, wenn zwischen den Aufrufen ein anderer Thread dazwischenkommt. Halten Threads mehrere Monitore und warten aufeinander, entstehen Deadlocks. Bei virtuellen Threads in Java 21 ist <code>ReentrantLock</code> oft die bessere Wahl, weil ein virtueller Thread in einem <code>synchronized</code>-Block seinen Träger-Thread blockiert. Seit Java 24 ist dieses Problem behoben.</p>
<h3>In der Praxis</h3>
<p><code>synchronized</code>-Methoden und -Blöcke, <code>ReentrantLock</code>, <code>Collections.synchronizedList()</code>, ältere Klassen wie <code>Vector</code> und <code>Hashtable</code>. Für einfache Zähler sind <code>AtomicLong</code> und <code>LongAdder</code> schneller als ein Monitor.</p>

<h3>Die Idee</h3>
<p>Lesen verändert nichts, deshalb dürfen <strong>beliebig viele Leser gleichzeitig</strong> zugreifen. Nur wer <strong>schreibt</strong>, braucht exklusiven Zugriff: Während eines Schreibvorgangs darf weder ein anderer Schreiber noch ein Leser zugreifen. Eine Read-Write Lock verwaltet zwei zusammengehörige Sperren, eine geteilte zum Lesen und eine exklusive zum Schreiben.</p>
<h3>Im Code</h3>
<p>Eine Preisliste wird 200-mal gelesen und viermal geändert. Die Messung zeigt: Mehrere Leser waren gleichzeitig aktiv, aber während eines Schreibvorgangs las kein einziger. Mit einer normalen Sperre hätten alle 200 Leser nacheinander warten müssen.</p>
<details class="code"><summary>Java-21-Code: ReadWriteLock.java</summary><p>Direkt ausführbar mit <code>java ReadWriteLock.java</code></p><pre><code class="language-java">// Read-Write Lock
// Beliebig viele Leser dürfen gleichzeitig lesen. Wer schreibt, bekommt exklusiven Zugriff.
// Start: java ReadWriteLock.java

import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.locks.ReentrantReadWriteLock;

public class ReadWriteLock {

    static final class Preisliste {
        private final ReentrantReadWriteLock sperre = new ReentrantReadWriteLock();
        private final Map&lt;String, Long&gt; preise = new HashMap&lt;&gt;(Map.of(&quot;Buch&quot;, 1_990L, &quot;Lampe&quot;, 3_990L));

        // Messwerte für die Demonstration
        final AtomicInteger leserJetzt = new AtomicInteger();
        final AtomicInteger leserMaximal = new AtomicInteger();
        final AtomicInteger leserWaehrendSchreiben = new AtomicInteger();
        private volatile boolean schreibtGerade;

        long preis(String artikel) throws InterruptedException {
            sperre.readLock().lock();                                // viele gleichzeitig erlaubt
            try {
                int n = leserJetzt.incrementAndGet();
                leserMaximal.accumulateAndGet(n, Math::max);
                if (schreibtGerade) leserWaehrendSchreiben.incrementAndGet();
                Thread.sleep(20);                                    // Lesen dauert etwas
                return preise.get(artikel);
            } finally {
                leserJetzt.decrementAndGet();
                sperre.readLock().unlock();
            }
        }

        void setzePreis(String artikel, long cent) throws InterruptedException {
            sperre.writeLock().lock();                               // exklusiv: keine Leser, keine anderen Schreiber
            try {
                schreibtGerade = true;
                Thread.sleep(50);
                preise.put(artikel, cent);
            } finally {
                schreibtGerade = false;
                sperre.writeLock().unlock();
            }
        }
    }

    public static void main(String[] args) {
        Preisliste liste = new Preisliste();
        try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i &lt; 200; i++) {
                ex.submit(() -&gt; liste.preis(&quot;Buch&quot;));                // viele Leser
                if (i % 50 == 0) ex.submit(() -&gt; { liste.setzePreis(&quot;Buch&quot;, 1_790); return null; });   // wenige Schreiber
            }
        }
        System.out.println(&quot;200 Lesezugriffe, 4 Schreibzugriffe:&quot;);
        System.out.println(&quot;  mehrere Leser gleichzeitig:    &quot; + (liste.leserMaximal.get() &gt; 1));
        System.out.println(&quot;  Leser während eines Schreibens: &quot; + liste.leserWaehrendSchreiben.get());
    }
}</code></pre><p><strong>Ausgabe</strong></p><pre><code>200 Lesezugriffe, 4 Schreibzugriffe:
  mehrere Leser gleichzeitig:    true
  Leser während eines Schreibens: 0</code></pre></details>
<h3>Worauf achten</h3>
<p>Der Gewinn tritt nur ein, wenn deutlich <strong>mehr gelesen als geschrieben</strong> wird und das Lesen eine gewisse Zeit dauert. Bei kurzen Zugriffen ist eine Read-Write Lock wegen ihres Verwaltungsaufwands oft langsamer als eine einfache Sperre. Schreiber können „verhungern“, wenn ständig neue Leser kommen. <code>ReentrantReadWriteLock</code> kann deshalb im fairen Modus betrieben werden. Eine Lesesperre lässt sich nicht in eine Schreibsperre umwandeln, der Versuch führt zum Deadlock. Oft ist ein <em>Immutable Object</em> (Muster 44), das bei Änderungen komplett ausgetauscht wird, die einfachere Lösung.</p>
<h3>In der Praxis</h3>
<p><code>ReentrantReadWriteLock</code>, <code>StampedLock</code> mit optimistischem Lesen ohne Sperre, <code>ConcurrentHashMap</code>, die Leser grundsätzlich nicht blockiert, <code>CopyOnWriteArrayList</code> für sehr selten geänderte Listen. In Datenbanken entsprechen geteilte und exklusive Sperren demselben Prinzip.</p>

<h3>Die Idee</h3>
<p>Statt für jede Verbindung einen eigenen Thread zu reservieren, wartet beim Reactor <strong>ein einziger Thread</strong> auf Ereignisse <strong>aller Quellen gleichzeitig</strong>: neue Verbindung, Daten angekommen, Verbindung geschlossen. Sobald etwas passiert, ruft er den dafür registrierten <strong>Handler</strong> auf und wartet dann wieder. Diese Schleife heißt <em>Event-Loop</em>. Das Muster stammt von Douglas Schmidt (POSA 2).</p>
<h3>Im Code</h3>
<p>Die Klasse <code>EventLoop</code> nimmt Ereignisse aus einer Warteschlange, die hier für den Selector des Betriebssystems steht, und verteilt sie an die registrierten Handler. Drei Verbindungen schicken zehn Ereignisse verzahnt. Alle werden vom einzigen Thread <code>reactor</code> verarbeitet. Die Sitzungsdaten liegen in einer gewöhnlichen <code>HashMap</code>, ohne Sperren.</p>
<details class="code"><summary>Java-21-Code: Reactor.java</summary><p>Direkt ausführbar mit <code>java Reactor.java</code></p><pre><code class="language-java">// Reactor
// Ein einziger Thread wartet auf Ereignisse aus vielen Quellen und verteilt sie an die zuständigen Handler.
// Start: java Reactor.java

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.LinkedBlockingQueue;
import java.util.function.Consumer;

public class Reactor {

    enum Art { VERBINDUNG, DATEN, GESCHLOSSEN }
    record Ereignis(Art art, String quelle, String inhalt) {}

    // --- Der Reactor: Ereignisschleife + Verteilung an registrierte Handler ---
    static final class EventLoop {
        private final BlockingQueue&lt;Ereignis&gt; eingang = new LinkedBlockingQueue&lt;&gt;();   // steht für den Selector
        private final Map&lt;Art, Consumer&lt;Ereignis&gt;&gt; handler = new HashMap&lt;&gt;();

        void registriere(Art art, Consumer&lt;Ereignis&gt; h) { handler.put(art, h); }
        void melde(Ereignis e) { eingang.add(e); }                     // von außen: &quot;hier ist etwas passiert&quot;
        void stopp() { eingang.add(new Ereignis(null, &quot;&quot;, &quot;&quot;)); }      // Stopp-Ereignis, nach allen anderen

        void starte() throws InterruptedException {
            while (true) {
                Ereignis e = eingang.take();                           // warten, bis etwas passiert (demultiplexen)
                if (e.art() == null) return;
                handler.getOrDefault(e.art(), x -&gt; {}).accept(e);      // an den Handler verteilen (dispatch)
            }
        }
    }

    public static void main(String[] args) throws Exception {
        EventLoop reactor = new EventLoop();
        Map&lt;String, List&lt;String&gt;&gt; sitzungen = new HashMap&lt;&gt;();         // kein Locking nötig: nur EIN Thread

        reactor.registriere(Art.VERBINDUNG, e -&gt; {
            sitzungen.put(e.quelle(), new ArrayList&lt;&gt;());
            System.out.println(&quot;  [&quot; + Thread.currentThread().getName() + &quot;] neu:     &quot; + e.quelle());
        });
        reactor.registriere(Art.DATEN, e -&gt; {
            sitzungen.get(e.quelle()).add(e.inhalt());
            System.out.println(&quot;  [&quot; + Thread.currentThread().getName() + &quot;] Daten:   &quot; + e.quelle() + &quot; -&gt; &quot; + e.inhalt());
        });
        reactor.registriere(Art.GESCHLOSSEN, e -&gt; {
            System.out.println(&quot;  [&quot; + Thread.currentThread().getName() + &quot;] Ende:    &quot; + e.quelle() + &quot;, empfangen: &quot; + sitzungen.remove(e.quelle()));
        });

        Thread schleife = Thread.ofPlatform().name(&quot;reactor&quot;).start(() -&gt; {
            try { reactor.starte(); } catch (InterruptedException ignored) { }
        });

        // Viele &quot;Verbindungen&quot; melden Ereignisse, verzahnt
        String[][] ablauf = {
                { &quot;VERBINDUNG&quot;, &quot;Kunde-A&quot;, &quot;&quot; }, { &quot;VERBINDUNG&quot;, &quot;Kunde-B&quot;, &quot;&quot; },
                { &quot;DATEN&quot;, &quot;Kunde-A&quot;, &quot;GET /warenkorb&quot; }, { &quot;DATEN&quot;, &quot;Kunde-B&quot;, &quot;GET /suche?q=lampe&quot; },
                { &quot;VERBINDUNG&quot;, &quot;Kunde-C&quot;, &quot;&quot; }, { &quot;DATEN&quot;, &quot;Kunde-A&quot;, &quot;POST /bestellung&quot; },
                { &quot;GESCHLOSSEN&quot;, &quot;Kunde-B&quot;, &quot;&quot; }, { &quot;DATEN&quot;, &quot;Kunde-C&quot;, &quot;GET /&quot; },
                { &quot;GESCHLOSSEN&quot;, &quot;Kunde-A&quot;, &quot;&quot; }, { &quot;GESCHLOSSEN&quot;, &quot;Kunde-C&quot;, &quot;&quot; } };
        for (String[] z : ablauf) reactor.melde(new Ereignis(Art.valueOf(z[0]), z[1], z[2]));

        reactor.stopp();
        schleife.join();
        System.out.println(&quot;\nDrei Verbindungen, zehn Ereignisse, ein einziger Thread.&quot;);
    }
}</code></pre><p><strong>Ausgabe</strong></p><pre><code>  [reactor] neu:     Kunde-A

<h3>Worauf achten</h3>
<p>Die goldene Regel: <strong>Ein Handler darf nie blockieren</strong>. Wartet er auf eine Datenbank oder rechnet lange, stehen alle anderen Verbindungen still. Langwierige Arbeit wird deshalb an einen Thread-Pool abgegeben. Code im Reactor-Stil ist schwerer zu lesen als einfacher blockierender Code, weil der Ablauf über viele Rückrufe verteilt ist. Mit virtuellen Threads in Java 21 lässt sich dieselbe Skalierbarkeit in vielen Fällen mit einfachem Code „ein Thread pro Verbindung“ erreichen.</p>
<h3>In der Praxis</h3>
<p><code>java.nio.channels.Selector</code> als Demultiplexer, Netty und Vert.x als Reactor-Frameworks, Node.js mit seiner Event-Loop, nginx, Redis, Spring WebFlux über Reactor Netty. Unter Linux liegt meist <code>epoll</code> darunter.</p>

<h3>Die Idee</h3>
<p>Beide Muster beantworten dieselbe Frage: Was tun, wenn ein Aufruf eintrifft, aber der Zustand ihn gerade nicht zulässt?</p>
<ul>
<li><strong>Balking</strong> (zögern, sich weigern): Die Methode prüft die Bedingung und <strong>kehrt sofort zurück</strong>, wenn sie nicht erfüllt ist. Typisch, wenn die Aktion dann sinnlos wäre: speichern, obwohl sich nichts geändert hat, oder ein zweiter Speichervorgang, während der erste noch läuft.</li>
<li><strong>Guarded Suspension</strong> (bewachtes Warten): Die Methode <strong>wartet</strong>, bis die Bedingung erfüllt ist. Ein anderer Thread stellt sie her und weckt die Wartenden. Typisch, wenn die Aktion später gelingen wird: Ware entnehmen, die gerade geliefert wird.</li>
</ul>
<h3>Im Code</h3>
<p>Das <code>Dokument</code> verweigert das Speichern, wenn nichts geändert wurde oder gerade gespeichert wird. Am Ende gibt es genau einen Speichervorgang. Das <code>Lager</code> lässt Kommissionierer mit <code>wait()</code> warten, bis eine Lieferung mit <code>notifyAll()</code> sie weckt. Kommissionierer 1 wartet nach der ersten Lieferung weiter, weil 2 Stück für ihn nicht reichen, und kommt nach der zweiten zum Zug.</p>
<details class="code"><summary>Java-21-Code: BalkingGuardedSuspension.java</summary><p>Direkt ausführbar mit <code>java BalkingGuardedSuspension.java</code></p><pre><code class="language-java">// Balking und Guarded Suspension
// Zwei Antworten auf dieselbe Frage: Was tun, wenn eine Aktion gerade nicht möglich ist?
//   Balking:            sofort aufgeben (&quot;lohnt sich nicht&quot;)
//   Guarded Suspension: warten, bis es möglich ist
// Start: java BalkingGuardedSuspension.java

import java.util.concurrent.Executors;

public class BalkingGuardedSuspension {

    // --- Balking: Speichern nur, wenn es etwas zu speichern gibt und nicht schon gespeichert wird ---
    static final class Dokument {
        private boolean geaendert;
        private boolean speichertGerade;
        private int speichervorgaenge;

        synchronized void bearbeite() { geaendert = true; }

        void speichere(String wer) throws InterruptedException {
            synchronized (this) {
                if (!geaendert || speichertGerade) {                      // Bedingung nicht erfüllt -&gt; abbrechen
                    System.out.println(&quot;  &quot; + wer + &quot;: &quot; + (speichertGerade ? &quot;wird gerade gespeichert&quot; : &quot;nichts geändert&quot;) + &quot;, breche ab&quot;);
                    return;
                }
                speichertGerade = true;
            }
            Thread.sleep(50);                                            // langsames Schreiben, ohne Sperre
            synchronized (this) {
                geaendert = false;
                speichertGerade = false;
                speichervorgaenge++;
                System.out.println(&quot;  &quot; + wer + &quot;: gespeichert&quot;);
            }
        }
        synchronized int speichervorgaenge() { return speichervorgaenge; }
    }

    // --- Guarded Suspension: Entnahme wartet, bis genug Bestand da ist ---
    static final class Lager {
        private int bestand;

        synchronized void entnehme(int menge, String wer) throws InterruptedException {
            while (bestand &lt; menge) {                                    // Wächterbedingung, immer in einer Schleife
                System.out.println(&quot;  &quot; + wer + &quot; wartet auf &quot; + menge + &quot; Stück (Bestand &quot; + bestand + &quot;)&quot;);
                wait();                                                  // Sperre freigeben und schlafen
            }
            bestand -= menge;
            System.out.println(&quot;  &quot; + wer + &quot; entnimmt &quot; + menge + &quot; Stück (Rest &quot; + bestand + &quot;)&quot;);
        }

        synchronized void liefere(int menge) {
            bestand += menge;
            System.out.println(&quot;  Lieferung: +&quot; + menge + &quot; (Bestand &quot; + bestand + &quot;)&quot;);
            notifyAll();                                                 // Wartende wecken
        }
    }

    public static void main(String[] args) throws Exception {
        System.out.println(&quot;Balking: Autosave und Benutzer wollen gleichzeitig speichern&quot;);
        Dokument doc = new Dokument();
        doc.speichere(&quot;Autosave (vor jeder Änderung)&quot;);
        doc.bearbeite();
        Thread t = Thread.ofVirtual().start(() -&gt; { try { doc.speichere(&quot;Autosave&quot;); } catch (InterruptedException ignored) { } });
        Thread.sleep(10);
        doc.speichere(&quot;Benutzer&quot;);                                       // Autosave läuft gerade
        t.join();
        System.out.println(&quot;  Speichervorgänge insgesamt: &quot; + doc.speichervorgaenge());

        System.out.println(&quot;\nGuarded Suspension: Kommissionierer warten auf Ware&quot;);
        Lager lager = new Lager();
        try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
            ex.submit(() -&gt; { lager.entnehme(3, &quot;Kommissionierer 1&quot;); return null; });
            Thread.sleep(50);
            ex.submit(() -&gt; { lager.entnehme(2, &quot;Kommissionierer 2&quot;); return null; });
            Thread.sleep(50);
            lager.liefere(2);
            Thread.sleep(50);
            lager.liefere(5);
        }
    }
}</code></pre><p><strong>Ausgabe</strong></p><pre><code>Balking: Autosave und Benutzer wollen gleichzeitig speichern
  Autosave (vor jeder Änderung): nichts geändert, breche ab
  Benutzer: wird gerade gespeichert, breche ab
  Autosave: gespeichert
  Speichervorgänge insgesamt: 1

Guarded Suspension: Kommissionierer warten auf Ware
  Kommissionierer 1 wartet auf 3 Stück (Bestand 0)
  Kommissionierer 2 wartet auf 2 Stück (Bestand 0)
  Lieferung: +2 (Bestand 2)
  Kommissionierer 1 wartet auf 3 Stück (Bestand 2)
  Kommissionierer 2 entnimmt 2 Stück (Rest 0)
  Lieferung: +5 (Bestand 5)
  Kommissionierer 1 entnimmt 3 Stück (Rest 2)</code></pre></details>
<h3>Worauf achten</h3>
<p>Die Wächterbedingung muss immer in einer <strong><code>while</code>-Schleife</strong> geprüft werden, nie in einem <code>if</code>. Ein geweckter Thread muss erneut prüfen, weil ein anderer ihm zuvorgekommen sein kann oder er ohne Grund aufwacht (<em>spurious wakeup</em>). <code>notifyAll()</code> ist sicherer als <code>notify()</code>, das nur einen beliebigen Wartenden weckt. Bei Guarded Suspension ist fast immer ein <strong>Zeitlimit</strong> sinnvoll, damit ein Thread nicht ewig wartet. In modernem Java nimmt man statt <code>wait()</code>/<code>notifyAll()</code> meist eine <code>BlockingQueue</code>, eine <code>Condition</code> oder einen <code>Semaphore</code>.</p>
<h3>In der Praxis</h3>
<p>Balking: Autosave-Funktionen, das Abfangen von Doppelklicks auf „Bestellen“, Initialisierungen, die nur einmal laufen sollen. Guarded Suspension: <code>BlockingQueue.take()</code>, <code>CountDownLatch.await()</code>, <code>Condition.await()</code> zusammen mit <code>ReentrantLock</code>.</p>

<h3>Die Idee</h3>
<p>Ein Objekt, das sich nach seiner Erzeugung <strong>nie mehr verändert</strong>, kann ohne jede Absicherung von beliebig vielen Threads gleichzeitig gelesen werden. Es gibt nichts, was sich zwischen zwei Zugriffen ändern könnte. „Ändern“ heißt dann: eine neue Version erzeugen. Wer die aktuelle Version braucht, holt sie sich über eine einzige, atomar austauschbare Referenz.</p>
<h3>Im Code</h3>
<p>Die <code>Preisliste</code> ist ein Record mit defensiven Kopien im Konstruktor. Ändert jemand nachträglich die übergebene Liste, bleibt die Preisliste unberührt, und auch über den Getter lässt sich nichts hinzufügen. <code>mitPreis()</code> liefert eine neue Version. Eine <code>AtomicReference</code> zeigt auf die aktuelle Version. 1.000 Leser greifen ohne Sperre zu, 100 Schreiber setzen per <code>updateAndGet</code> neue Versionen ein, und am Ende stimmen Preis und Versionsnummer exakt.</p>
<details class="code"><summary>Java-21-Code: ImmutableObject.java</summary><p>Direkt ausführbar mit <code>java ImmutableObject.java</code></p><pre><code class="language-java">// Immutable Object
// Ein Objekt, das nach seiner Erzeugung nie mehr verändert wird, ist automatisch threadsicher.
// Start: java ImmutableObject.java

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicReference;

public class ImmutableObject {

    // --- Unveränderlich: final, keine Setter, Kopien von veränderlichen Eingaben ---
    record Preisliste(int version, Map&lt;String, Long&gt; preise, List&lt;String&gt; aktionen) {
        Preisliste {
            preise = Map.copyOf(preise);           // defensive Kopie: spätere Änderungen am Original wirken nicht
            aktionen = List.copyOf(aktionen);
        }
        // &quot;Ändern&quot; heißt: neue Instanz liefern
        Preisliste mitPreis(String artikel, long cent) {
            Map&lt;String, Long&gt; neu = new TreeMap&lt;&gt;(preise);
            neu.put(artikel, cent);
            return new Preisliste(version + 1, neu, aktionen);
        }
        public String toString() { return &quot;v&quot; + version + &quot; &quot; + new TreeMap&lt;&gt;(preise) + &quot; &quot; + aktionen; }
    }

    public static void main(String[] args) throws Exception {
        List&lt;String&gt; aktionen = new ArrayList&lt;&gt;(List.of(&quot;Herbstrabatt&quot;));
        Preisliste v1 = new Preisliste(1, Map.of(&quot;Buch&quot;, 1_990L, &quot;Lampe&quot;, 3_990L), aktionen);

        aktionen.add(&quot;heimlich hinzugefügt&quot;);      // ändert die Preisliste NICHT
        System.out.println(&quot;v1 nach Änderung der Eingabeliste: &quot; + v1);

        try { v1.aktionen().add(&quot;Hack&quot;); }
        catch (UnsupportedOperationException e) { System.out.println(&quot;v1.aktionen().add(...) -&gt; abgelehnt&quot;); }

        Preisliste v2 = v1.mitPreis(&quot;Buch&quot;, 1_790);
        System.out.println(&quot;v1 bleibt: &quot; + v1);
        System.out.println(&quot;v2 neu:    &quot; + v2);

        // --- Teilen zwischen Threads: lesen ohne Sperren, austauschen per AtomicReference ---
        AtomicReference&lt;Preisliste&gt; aktuell = new AtomicReference&lt;&gt;(v2);
        try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i &lt; 1_000; i++) ex.submit(() -&gt; aktuell.get().preise().get(&quot;Lampe&quot;));     // 1.000 Leser
            for (int i = 0; i &lt; 100; i++) ex.submit(() -&gt; aktuell.updateAndGet(p -&gt; p.mitPreis(&quot;Lampe&quot;, p.preise().get(&quot;Lampe&quot;) - 1)));
        }
        System.out.println(&quot;\nNach 1.000 Lesern und 100 Preissenkungen um je 1 Cent:&quot;);
        System.out.println(&quot;  &quot; + aktuell.get());
        System.out.println(&quot;  Lampe = 3990 - 100 = &quot; + aktuell.get().preise().get(&quot;Lampe&quot;) + &quot;, Version &quot; + aktuell.get().version());
    }
}</code></pre><p><strong>Ausgabe</strong></p><pre><code>v1 nach Änderung der Eingabeliste: v1 {Buch=1990, Lampe=3990} [Herbstrabatt]
v1.aktionen().add(...) -&gt; abgelehnt
v1 bleibt: v1 {Buch=1990, Lampe=3990} [Herbstrabatt]
v2 neu:    v2 {Buch=1790, Lampe=3990} [Herbstrabatt]

Nach 1.000 Lesern und 100 Preissenkungen um je 1 Cent:
  v102 {Buch=1790, Lampe=3890} [Herbstrabatt]
  Lampe = 3990 - 100 = 3890, Version 102</code></pre></details>
<h3>Worauf achten</h3>
<p>Ein Objekt ist nur dann wirklich unveränderlich, wenn <strong>alle Felder final</strong> sind, <strong>keine Methode etwas ändert</strong> und auch <strong>enthaltene Objekte</strong> unveränderlich sind oder kopiert werden. Ein Record mit einer <code>ArrayList</code> darin ist es nicht. Daher die Kopie mit <code>List.copyOf</code>. Bei großen Objekten, die oft geändert werden, kostet das ständige Kopieren Zeit und Speicher. Dafür gibt es persistente Datenstrukturen, die unveränderte Teile zwischen Versionen teilen. Das Muster vereinfacht nebenläufige Programme so stark, dass Joshua Bloch rät: „Klassen sollten unveränderlich sein, solange es keinen sehr guten Grund dagegen gibt.“</p>
<h3>In der Praxis</h3>
<p>Im JDK: <code>String</code>, <code>Integer</code>, <code>LocalDate</code>, <code>BigDecimal</code>, Records, <code>List.of()</code> und <code>Map.of()</code>. Konfigurationen, die zur Laufzeit komplett ausgetauscht werden, Zustände in Redux und in funktionalen Sprachen. Das <em>Value Object</em> aus Gruppe 2 ist fast immer zugleich ein Immutable Object.</p>
