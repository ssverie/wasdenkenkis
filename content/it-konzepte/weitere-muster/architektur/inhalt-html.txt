<h2 id="layers"><span class="nr">27.</span> Layers <span class="de">· Schichtenarchitektur</span></h2>
<figure class="diagramm"><svg viewBox="0 0 720 260" role="img" aria-label="Schichtenarchitektur: jede Schicht nutzt nur die darunterliegende" xmlns="http://www.w3.org/2000/svg"><defs><marker id="pfeil" viewBox="0 0 10 10" refX="9" refY="5" markerWidth="7" markerHeight="7" orient="auto-start-reverse"><path d="M0,0 L10,5 L0,10 z" class="head"/></marker></defs><rect x="120" y="16" width="420" height="46" rx="6" class="comp"/><text x="220" y="44" class="lbl" text-anchor="middle">Präsentation</text><text x="410" y="44" class="tiny" text-anchor="middle">Weboberfläche, REST-Controller</text><line x1="330" y1="62" x2="330" y2="74" class="arr" marker-end="url(#pfeil)"/><rect x="120" y="74" width="420" height="46" rx="6" class="comp"/><text x="220" y="102" class="lbl" text-anchor="middle">Anwendung</text><text x="410" y="102" class="tiny" text-anchor="middle">Anwendungsfälle, Transaktionen</text><line x1="330" y1="120" x2="330" y2="132" class="arr" marker-end="url(#pfeil)"/><rect x="120" y="132" width="420" height="46" rx="6" class="store"/><text x="220" y="160" class="lbl" text-anchor="middle">Domäne</text><text x="410" y="160" class="tiny" text-anchor="middle">Fachlogik, Entities, Regeln</text><line x1="330" y1="178" x2="330" y2="190" class="arr" marker-end="url(#pfeil)"/><rect x="120" y="190" width="420" height="46" rx="6" class="app"/><text x="220" y="218" class="lbl" text-anchor="middle">Infrastruktur</text><text x="410" y="218" class="tiny" text-anchor="middle">Datenbank, Mail, externe Dienste</text><path d="M560,200 C620,180 620,60 560,40" class="arr-leise" fill="none" stroke-dasharray="5 4" marker-end="url(#pfeil)"/><path d="M607,112 L623,128 M623,112 L607,128" class="cross"/><text x="640" y="124" class="tiny" text-anchor="start">nie nach oben</text><text x="60" y="130" class="note" text-anchor="middle">Abhängigkeit</text><text x="60" y="146" class="note" text-anchor="middle">nur nach unten</text></svg><figcaption>Vier klassische Schichten. Jede darf nur die darunterliegende verwenden, nie eine darüberliegende.</figcaption></figure>
<h3>Die Idee</h3>
<p>Die Anwendung wird in <strong>übereinanderliegende Schichten</strong> gegliedert, jede mit einer klaren Aufgabe. Eine Schicht darf nur die Dienste der Schicht <strong>unter ihr</strong> nutzen, nie die einer höheren. So bleibt jede Schicht austauschbar und verständlich, ohne dass man das ganze System kennen muss. Das Muster ist eines der ältesten der Softwarearchitektur und steht auch im POSA-Buch.</p>
<h3>Beispiel</h3>
<p>Ein Online-Shop hat vier Schichten: Die <strong>Präsentation</strong> nimmt Anfragen aus dem Browser entgegen. Die <strong>Anwendungsschicht</strong> setzt Anwendungsfälle wie „Bestellung aufgeben“ um und steuert Transaktionen. Die <strong>Domäne</strong> enthält die Fachlogik, etwa Preis- und Rabattregeln. Die <strong>Infrastruktur</strong> spricht mit Datenbank, Mailserver und externen Diensten. Wird die Weboberfläche durch eine App ersetzt, betrifft das nur die oberste Schicht.</p>
<h3>Worauf achten</h3>
<p>In der <strong>strikten</strong> Variante darf jede Schicht nur die direkt darunterliegende nutzen, in der <strong>gelockerten</strong> alle tieferen. Ein bekanntes Problem: In der klassischen Anordnung hängt die Domäne von der Infrastruktur ab, die Fachlogik also von der Datenbanktechnik. Genau das kehren die <em>Hexagonal Architecture</em> (Muster 29) und verwandte Ansätze wie Clean Architecture um. Zu viele Schichten erzeugen außerdem reine Durchreichcode, bei dem jede Schicht nur die nächste aufruft, ohne selbst etwas zu tun.</p>
<h3>In der Praxis</h3>
<p>Die typische Spring-Anwendung mit <code>@Controller</code>, <code>@Service</code> und <code>@Repository</code>, das OSI-Modell und TCP/IP in Netzwerken, die Schichtung eines Betriebssystems von der Hardware bis zur Anwendung. Werkzeuge wie ArchUnit prüfen in Tests, dass keine verbotenen Abhängigkeiten zwischen Schichten entstehen.</p>

<h3>Die Idee</h3>
<p>MVC trennt eine Anwendung mit Benutzeroberfläche in drei Teile: Das <strong>Model</strong> enthält die Daten und Regeln und weiß nichts von ihrer Darstellung. Die <strong>View</strong> stellt das Model dar. Der <strong>Controller</strong> nimmt Eingaben des Benutzers entgegen und übersetzt sie in Änderungen am Model. Ändert sich das Model, werden die Views benachrichtigt, meist über das <em>Observer</em>-Muster. Erfunden wurde MVC 1979 von Trygve Reenskaug für Smalltalk.</p>
<h3>Im Code</h3>
<p>Der <code>Warenkorb</code> ist das Model mit Preisregeln und einer Liste von Beobachtern. Die <code>KopfzeilenView</code> zeigt bei jeder Änderung Anzahl und Summe, die <code>DetailView</code> listet die Positionen auf, beide über dasselbe Model. Der <code>WarenkorbController</code> wandelt Eingaben wie „+ Buch“ in Aufrufe am Model um und fängt Fehler ab.</p>
<details class="code"><summary>Java-21-Code: ModelViewController.java</summary><p>Direkt ausführbar mit <code>java ModelViewController.java</code></p><pre><code class="language-java">// Model-View-Controller (MVC)
// Trennt Daten und Logik (Model), Darstellung (View) und Eingabeverarbeitung (Controller).
// Start: java ModelViewController.java

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Locale;
import java.util.Map;
import java.util.function.Consumer;

public class ModelViewController {

    // ================= Model: Daten und Regeln, kennt keine Darstellung =================
    static final class Warenkorb {
        private final Map&lt;String, Integer&gt; positionen = new LinkedHashMap&lt;&gt;();
        private final Map&lt;String, Long&gt; preise = Map.of(&quot;Buch&quot;, 1_990L, &quot;Lampe&quot;, 3_990L, &quot;Tasse&quot;, 890L);
        private final List&lt;Consumer&lt;Warenkorb&gt;&gt; beobachter = new ArrayList&lt;&gt;();

        void beobachte(Consumer&lt;Warenkorb&gt; b) { beobachter.add(b); }

        void lege(String artikel, int menge) {
            if (!preise.containsKey(artikel)) throw new IllegalArgumentException(&quot;unbekannter Artikel: &quot; + artikel);
            positionen.merge(artikel, menge, Integer::sum);
            if (positionen.get(artikel) &lt;= 0) positionen.remove(artikel);
            beobachter.forEach(b -&gt; b.accept(this));              // Views benachrichtigen (Observer)
        }
        Map&lt;String, Integer&gt; positionen() { return java.util.Collections.unmodifiableMap(positionen); }
        long summe() { return positionen.entrySet().stream().mapToLong(e -&gt; preise.get(e.getKey()) * e.getValue()).sum(); }
        int anzahl() { return positionen.values().stream().mapToInt(Integer::intValue).sum(); }
    }

    // ================= Views: zwei verschiedene Darstellungen desselben Models =================
    static final class KopfzeilenView {
        void zeige(Warenkorb w) {
            System.out.printf(Locale.GERMANY, &quot;  [Kopfzeile] Warenkorb (%d) %.2f €%n&quot;, w.anzahl(), w.summe() / 100.0);
        }
    }
    static final class DetailView {
        void zeige(Warenkorb w) {
            w.positionen().forEach((a, m) -&gt; System.out.println(&quot;  [Details]   &quot; + m + &quot; × &quot; + a));
        }
    }

    // ================= Controller: nimmt Eingaben entgegen und ändert das Model =================
    static final class WarenkorbController {
        private final Warenkorb model;
        WarenkorbController(Warenkorb model) { this.model = model; }

        void eingabe(String befehl) {                              // z. B. aus einem Klick oder einer Anfrage
            System.out.println(&quot;Eingabe: &quot; + befehl);
            String[] t = befehl.split(&quot; &quot;);
            try {
                switch (t[0]) {
                    case &quot;+&quot; -&gt; model.lege(t[1], 1);
                    case &quot;-&quot; -&gt; model.lege(t[1], -1);
                    default -&gt; System.out.println(&quot;  unbekannter Befehl&quot;);
                }
            } catch (IllegalArgumentException e) {
                System.out.println(&quot;  Fehler: &quot; + e.getMessage());
            }
        }
    }

    public static void main(String[] args) {
        Warenkorb model = new Warenkorb();
        KopfzeilenView kopf = new KopfzeilenView();
        model.beobachte(kopf::zeige);                              // die Kopfzeile zeigt jede Änderung
        WarenkorbController controller = new WarenkorbController(model);

        controller.eingabe(&quot;+ Buch&quot;);
        controller.eingabe(&quot;+ Buch&quot;);
        controller.eingabe(&quot;+ Lampe&quot;);
        controller.eingabe(&quot;+ Fahrrad&quot;);
        controller.eingabe(&quot;- Buch&quot;);

        System.out.println(&quot;Warenkorb-Seite öffnen:&quot;);
        new DetailView().zeige(model);                             // zweite View auf dasselbe Model
    }

<h3>Worauf achten</h3>
<p>„MVC“ bezeichnet heute viele leicht unterschiedliche Dinge. In Web-Frameworks wie Spring MVC verarbeitet der Controller eine HTTP-Anfrage, lädt Daten und gibt sie an ein Template weiter. Die Benachrichtigung des Models an die View fällt dort weg. Der häufigste Fehler ist der „fette Controller“, in den die Geschäftslogik wandert. Sie gehört ins Model bzw. in die darunterliegenden Schichten.</p>
<h3>In der Praxis</h3>
<p>Spring MVC und Jakarta MVC, Ruby on Rails, ASP.NET MVC, JavaFX mit Properties und Bindings (MVVM), Angular und Vue (MVVM-artig), Swing mit getrennten Models wie <code>TableModel</code>.</p>

<h3>Die Idee</h3>
<p>Die Hexagonal Architecture von Alistair Cockburn (2005), auch <em>Ports and Adapters</em> genannt, stellt die <strong>Fachlogik in die Mitte</strong>. Der Kern definiert <strong>Ports</strong>, also Schnittstellen in seiner eigenen Sprache: eingehende für das, was er anbietet, und ausgehende für das, was er von außen braucht. Alle Technik, Web, Datenbank, Mail, Messaging, wird über <strong>Adapter</strong> angeschlossen, die diese Ports bedienen oder implementieren. Die Abhängigkeiten zeigen immer von außen nach innen, nie umgekehrt. Das Sechseck hat keine besondere Bedeutung, es soll nur zeigen, dass es viele gleichberechtigte Seiten gibt, nicht „oben“ und „unten“ wie bei Schichten.</p>
<h3>Im Code</h3>
<p>Der <code>BestellService</code> implementiert den eingehenden Port <code>BestellenUseCase</code> und nutzt die ausgehenden Ports <code>BestellungenSpeichern</code> und <code>KundeBenachrichtigen</code>. Derselbe Kern wird über einen REST-Adapter und einen Kommandozeilen-Adapter angesprochen und läuft einmal mit SQL und E-Mail, einmal mit Test-Adaptern ganz ohne Infrastruktur.</p>
<details class="code"><summary>Java-21-Code: HexagonalArchitecture.java</summary><p>Direkt ausführbar mit <code>java HexagonalArchitecture.java</code></p><pre><code class="language-java">// Hexagonal Architecture (Ports &amp; Adapters)
// Der fachliche Kern definiert Ports (Schnittstellen). Technik wird über austauschbare Adapter angeschlossen.
// Start: java HexagonalArchitecture.java

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;

public class HexagonalArchitecture {

    // ======================= KERN: kennt keine Technik =======================
    record Bestellung(long nr, String kunde, long cent) {}

    // Eingehender Port: was die Anwendung anbietet
    interface BestellenUseCase {
        long bestelle(String kunde, long cent);
    }

    // Ausgehende Ports: was die Anwendung von außen braucht
    interface BestellungenSpeichern { void speichere(Bestellung b); Optional&lt;Bestellung&gt; lade(long nr); }
    interface KundeBenachrichtigen  { void bestaetige(Bestellung b); }

    // Die Fachlogik: implementiert den eingehenden Port, nutzt die ausgehenden
    static final class BestellService implements BestellenUseCase {
        private final BestellungenSpeichern speicher;
        private final KundeBenachrichtigen benachrichtigung;
        private long naechsteNr = 1000;

        BestellService(BestellungenSpeichern s, KundeBenachrichtigen b) { this.speicher = s; this.benachrichtigung = b; }

        public long bestelle(String kunde, long cent) {
            if (cent &lt;= 0) throw new IllegalArgumentException(&quot;Betrag muss positiv sein&quot;);
            Bestellung b = new Bestellung(++naechsteNr, kunde, cent);
            speicher.speichere(b);
            benachrichtigung.bestaetige(b);
            return b.nr();
        }
    }

    // ======================= ADAPTER: Technik außen herum =======================
    // Treibender Adapter (links): z. B. REST, hier als einfache &quot;Anfrage&quot;
    static final class RestAdapter {
        private final BestellenUseCase useCase;
        RestAdapter(BestellenUseCase u) { this.useCase = u; }
        String post(String json) {                                  // {&quot;kunde&quot;:&quot;Sven&quot;,&quot;cent&quot;:4990}
            String kunde = json.replaceAll(&quot;.*\&quot;kunde\&quot;:\&quot;([^\&quot;]+)\&quot;.*&quot;, &quot;$1&quot;);
            long cent = Long.parseLong(json.replaceAll(&quot;.*\&quot;cent\&quot;:(\\d+).*&quot;, &quot;$1&quot;));
            return &quot;201 Created, Bestellung &quot; + useCase.bestelle(kunde, cent);
        }
    }
    // Treibender Adapter: Kommandozeile
    static final class CliAdapter {
        private final BestellenUseCase useCase;
        CliAdapter(BestellenUseCase u) { this.useCase = u; }
        void befehl(String zeile) {
            String[] t = zeile.split(&quot; &quot;);

<h3>Worauf achten</h3>
<p>Der Kern darf <strong>keine Abhängigkeit</strong> zu Frameworks, Datenbanken oder Web-Bibliotheken haben, auch keine Annotationen wie <code>@Entity</code>. Das macht ihn ohne Infrastruktur testbar und überlebt jeden Technologiewechsel. Der Preis sind zusätzliche Schnittstellen und Abbildungen zwischen Kernobjekten und Technikobjekten. Für einfache CRUD-Anwendungen ist das zu viel. Eng verwandt sind die <em>Onion Architecture</em> (Jeffrey Palermo) und die <em>Clean Architecture</em> (Robert C. Martin), die dasselbe Prinzip mit konzentrischen Ringen darstellen.</p>
<h3>In der Praxis</h3>
<p>Häufig in Microservices nach Domain-Driven Design. Java-Projekte gliedern sich dann oft in Pakete wie <code>domain</code>, <code>application.port.in</code>, <code>application.port.out</code> und <code>adapter.in.web</code>, <code>adapter.out.persistence</code>. Bibliotheken wie jMolecules und ArchUnit helfen, die Regeln einzuhalten.</p>

<h3>Die Idee</h3>
<p>Eine Verarbeitung wird in eine <strong>Kette unabhängiger Schritte</strong> zerlegt. Jeder Schritt (Filter) hat einen Eingang und einen Ausgang. Verbunden werden sie durch Pipes, die Daten weiterreichen. Kein Filter kennt seine Nachbarn, deshalb lassen sich Filter austauschen, umsortieren und wiederverwenden. Das Muster steht im POSA-Buch als Architekturmuster und bei den Enterprise Integration Patterns als Grundbaustein des Messaging.</p>
<h3>In Java</h3>
<p>Im Kleinen sind Java Streams ein Pipes-and-Filters-System: <code>liste.stream().filter(...).map(...).distinct().sorted()</code>. Jede Methode ist ein Filter, der Stream die Pipe. Im Großen verbinden Frameworks wie Apache Camel oder Spring Integration Filter über Nachrichtenkanäle.</p>
<p>Eine ausführliche Beschreibung mit Diagramm steht bei den <a href="/it-konzepte/integration-patterns/messaging-grundlagen/#pipes-and-filters">Enterprise Integration Patterns, Muster 7</a>.</p>

Er vermittelt Anfragen und Nachrichten an die richtige Stelle.</figcaption></figure>
<h3>Die Idee</h3>
<p>Ein Broker ist ein <strong>Vermittler</strong> zwischen verteilten Komponenten. Statt einander direkt zu kennen, schicken die Komponenten ihre Anfragen oder Nachrichten an den Broker, der sie an den passenden Empfänger weiterleitet und Antworten zurückbringt. Das entkoppelt die Komponenten: Wo ein Dienst läuft, in welcher Sprache er geschrieben ist und wie viele Instanzen es gibt, ist für den Aufrufer unsichtbar.</p>
<h3>Varianten</h3>
<p>Das POSA-Buch beschreibt vor allem den Broker für <strong>entfernte Aufrufe</strong>, wie ihn CORBA mit dem Object Request Broker umsetzt. Heute ist der Begriff vor allem für <strong>Message Broker</strong> gebräuchlich: RabbitMQ, ActiveMQ, Kafka. Auch ein API-Gateway oder ein Service Mesh übernimmt Teile der Broker-Rolle.</p>
<p>Eine ausführliche Beschreibung mit Vergleich zur direkten Verbindung aller Systeme steht bei den <a href="/it-konzepte/integration-patterns/routing/#message-broker">Enterprise Integration Patterns, Muster 40</a>.</p>

Versand, Express, Betrugsprüfung und künftige Funktionen kommen als Plugins hinzu.</figcaption></figure>
<h3>Die Idee</h3>
<p>Beim Microkernel-Muster enthält der <strong>Kern nur das Nötigste</strong>: den Grundablauf und eine klar definierte Schnittstelle für Erweiterungen. Alle weiteren Funktionen werden als <strong>Plugins</strong> angeschlossen, die unabhängig entwickelt, ausgeliefert und aktiviert werden können. Der Name stammt von Betriebssystemen, deren Kern nur Prozesse und Speicher verwaltet, während Treiber und Dateisysteme außerhalb laufen.</p>
<h3>Im Code</h3>
<p>Der <code>Kern</code> verarbeitet Bestellungen, kennt aber weder Versandkosten noch Sonderregeln. Ohne Plugins ist jede Bestellung „nicht lieferbar“. Drei Plugins registrieren beim Start Versandkosten und reagieren auf jede Bestellung mit eigenen Notizen. Kein Plugin kennt ein anderes.</p>
<details class="code"><summary>Java-21-Code: Microkernel.java</summary><p>Direkt ausführbar mit <code>java Microkernel.java</code></p><pre><code class="language-java">// Microkernel / Plugin
// Ein minimaler Kern stellt die Grundfunktionen bereit. Alles Weitere kommt über Plugins hinzu.
// Start: java Microkernel.java

import java.util.ArrayList;
import java.util.List;
import java.util.Locale;
import java.util.Map;
import java.util.TreeMap;

public class Microkernel {

    record Bestellung(String nr, String land, long cent, boolean express) {}

    // --- Kontrakt zwischen Kern und Plugins ---
    interface Plugin {
        String name();
        default void beimStart(Kern kern) {}
        default void beiBestellung(Bestellung b, Map&lt;String, String&gt; notizen) {}
    }

    // --- Der Kern: nur das Nötigste ---
    static final class Kern {
        private final List&lt;Plugin&gt; plugins = new ArrayList&lt;&gt;();
        private final Map&lt;String, Long&gt; versandkosten = new TreeMap&lt;&gt;();

        void installiere(Plugin p) {
            plugins.add(p);
            p.beimStart(this);
            System.out.println(&quot;  Plugin geladen: &quot; + p.name());
        }
        void registriereVersand(String land, long cent) { versandkosten.put(land, cent); }   // Erweiterungspunkt

        void verarbeite(Bestellung b) {
            Map&lt;String, String&gt; notizen = new TreeMap&lt;&gt;();
            Long versand = versandkosten.get(b.land());
            notizen.put(&quot;versand&quot;, versand == null ? &quot;nicht lieferbar&quot; : String.format(Locale.GERMANY, &quot;%.2f €&quot;, versand / 100.0));
            plugins.forEach(p -&gt; p.beiBestellung(b, notizen));
            System.out.println(&quot;  &quot; + b.nr() + &quot; &quot; + notizen);
        }
    }

    // --- Plugins: unabhängig entwickelt, einzeln aktivierbar ---
    static final class VersandDACH implements Plugin {
        public String name() { return &quot;Versand DACH&quot;; }
        public void beimStart(Kern k) { k.registriereVersand(&quot;DE&quot;, 490); k.registriereVersand(&quot;AT&quot;, 790); k.registriereVersand(&quot;CH&quot;, 1490); }
    }
    static final class Expresszuschlag implements Plugin {
        public String name() { return &quot;Express&quot;; }
        public void beiBestellung(Bestellung b, Map&lt;String, String&gt; n) { if (b.express()) n.put(&quot;express&quot;, &quot;+9,90 €&quot;); }
    }
    static final class Betrugspruefung implements Plugin {
        public String name() { return &quot;Betrugsprüfung&quot;; }
        public void beiBestellung(Bestellung b, Map&lt;String, String&gt; n) { if (b.cent() &gt; 200_000) n.put(&quot;prüfung&quot;, &quot;manuell freigeben&quot;); }
    }

    public static void main(String[] args) {
        List&lt;Bestellung&gt; bestellungen = List.of(
                new Bestellung(&quot;B-1&quot;, &quot;DE&quot;, 4_990, false),
                new Bestellung(&quot;B-2&quot;, &quot;CH&quot;, 250_000, true));

        System.out.println(&quot;Nur der Kern:&quot;);
        Kern nackt = new Kern();
        bestellungen.forEach(nackt::verarbeite);

        System.out.println(&quot;\nKern mit drei Plugins:&quot;);
        Kern kern = new Kern();
        // In echten Systemen findet der Kern seine Plugins selbst, z. B. per java.util.ServiceLoader
        for (Plugin p : List.of(new VersandDACH(), new Expresszuschlag(), new Betrugspruefung())) kern.installiere(p);
        bestellungen.forEach(kern::verarbeite);
    }
}</code></pre><p><strong>Ausgabe</strong></p><pre><code>Nur der Kern:
  B-1 {versand=nicht lieferbar}
  B-2 {versand=nicht lieferbar}

Kern mit drei Plugins:
  Plugin geladen: Versand DACH
  Plugin geladen: Express
  Plugin geladen: Betrugsprüfung
  B-1 {versand=4,90 €}
  B-2 {express=+9,90 €, prüfung=manuell freigeben, versand=14,90 €}</code></pre></details>
<h3>Worauf achten</h3>
<p>Das Herzstück ist der <strong>Plugin-Vertrag</strong>: Er muss stabil bleiben, denn jede Änderung betrifft alle Plugins. Man braucht Regeln für Reihenfolge, Abhängigkeiten zwischen Plugins und Fehler: Darf ein abstürzendes Plugin den ganzen Kern mitreißen? Microkernel lohnt sich für Produkte, die bei verschiedenen Kunden unterschiedlich erweitert werden, weniger für eine einzelne, interne Anwendung.</p>
<h3>In der Praxis</h3>
<p>Die Eclipse-IDE und IntelliJ IDEA, deren gesamte Funktionalität aus Plugins besteht, Browser mit Erweiterungen, Jenkins, Maven und Gradle mit ihren Plugins, OSGi als Plugin-Plattform für Java. Plugins werden in Java oft über <code>java.util.ServiceLoader</code> oder das Modulsystem gefunden.</p>

<h3>Die Idee</h3>
<p>Beim Blackboard-Muster arbeiten mehrere <strong>unabhängige Spezialisten</strong> (Wissensquellen) an einem gemeinsamen Datenbestand, der <strong>Tafel</strong>. Jeder schaut, ob er mit dem, was dort steht, etwas beitragen kann, und schreibt sein Ergebnis dazu. Eine Steuerung entscheidet, wer als Nächstes an der Reihe ist. Wie Experten vor einer Wandtafel, die gemeinsam ein Problem lösen, ohne dass einer allein den ganzen Lösungsweg kennt.</p>
<h3>Im Code</h3>
<p>Bei jeder Bestellung prüfen drei Spezialisten Betrag, Kundenhistorie und Lieferadresse und schreiben ein Teilrisiko auf die Tafel. Der Entscheider wird erst aktiv, wenn alle drei Teilergebnisse vorliegen. Die Steuerung fragt reihum, wer beitragen kann, bis eine Entscheidung steht. Die Reihenfolge der Spezialisten in der Liste spielt keine Rolle.</p>
<details class="code"><summary>Java-21-Code: Blackboard.java</summary><p>Direkt ausführbar mit <code>java Blackboard.java</code></p><pre><code class="language-java">// Blackboard
// Mehrere unabhängige Spezialisten arbeiten an einem gemeinsamen Datenbestand, bis eine Lösung entsteht.
// Start: java Blackboard.java

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;

public class Blackboard {

    // --- Die Tafel: gemeinsamer Datenbestand, auf den alle schauen ---
    static final class Tafel {
        final Map&lt;String, Object&gt; eintraege = new TreeMap&lt;&gt;();
        boolean hat(String k) { return eintraege.containsKey(k); }
        int zahl(String k)    { return (int) eintraege.getOrDefault(k, 0); }
        void schreibe(String quelle, String k, Object v) {
            eintraege.put(k, v);
            System.out.println(&quot;  &quot; + quelle + &quot;: &quot; + k + &quot; = &quot; + v);
        }
    }

    // --- Wissensquellen: jede kann nur einen Teil, und meldet sich, wenn sie etwas beitragen kann ---
    interface Wissensquelle {
        String name();
        boolean kannBeitragen(Tafel t);
        void trageBei(Tafel t);
    }

    record AdressPruefung() implements Wissensquelle {
        public String name() { return &quot;Adressprüfung&quot;; }
        public boolean kannBeitragen(Tafel t) { return t.hat(&quot;lieferadresse&quot;) &amp;&amp; !t.hat(&quot;adresse_risiko&quot;); }
        public void trageBei(Tafel t) {
            boolean packstation = t.eintraege.get(&quot;lieferadresse&quot;).toString().contains(&quot;Packstation&quot;);
            t.schreibe(name(), &quot;adresse_risiko&quot;, packstation ? 30 : 0);
        }
    }
    record KundenHistorie() implements Wissensquelle {
        public String name() { return &quot;Kundenhistorie&quot;; }

        public String name() { return &quot;Entscheider&quot;; }
        public boolean kannBeitragen(Tafel t) {
            return t.hat(&quot;adresse_risiko&quot;) &amp;&amp; t.hat(&quot;historie_risiko&quot;) &amp;&amp; t.hat(&quot;betrag_risiko&quot;) &amp;&amp; !t.hat(&quot;entscheidung&quot;);

            t.schreibe(name(), &quot;entscheidung&quot;, summe &gt;= 60 ? &quot;manuell prüfen&quot; : &quot;freigeben&quot;);

    static void loese(Tafel t, List&lt;Wissensquelle&gt; quellen) {

            for (Wissensquelle q : quellen) {
                if (q.kannBeitragen(t)) { q.trageBei(t); fortschritt = true; }
            }
        }

<h3>Die Idee</h3>
<p>Üblicherweise speichert eine Anwendung den <strong>aktuellen Zustand</strong>: Der Kontostand ist 1.000 €. Bei Event Sourcing speichert sie stattdessen die <strong>Folge aller Ereignisse</strong>, die zu diesem Zustand geführt haben: eröffnet, 1.000 € eingezahlt, 300 € abgehoben und so weiter. Der Zustand wird bei Bedarf berechnet, indem man die Ereignisse der Reihe nach „abspielt“. Ereignisse werden nur angehängt, nie geändert oder gelöscht. So arbeitet jede Buchhaltung seit Jahrhunderten: Man radiert keine Buchung aus, man bucht eine Korrektur.</p>
<h3>Im Code</h3>
<p>Die Ereignisse sind Records hinter einem <code>sealed</code> Interface. Der <code>EventStore</code> hängt nur an. Der Kontostand entsteht durch <code>Konto.aus(ereignisse)</code>, das jedes Ereignis per Pattern Matching anwendet. Befehle wie <code>hebeAb</code> prüfen gegen den berechneten Zustand und erzeugen nur dann ein neues Ereignis. Zum Schluss zwei Dinge, die mit einem normalen Zustandsspeicher unmöglich wären: der Kontostand an einem beliebigen Tag der Vergangenheit und eine neue Auswertung über alle bisherigen Einzahlungen.</p>
<details class="code"><summary>Java-21-Code: EventSourcing.java</summary><p>Direkt ausführbar mit <code>java EventSourcing.java</code></p><pre><code class="language-java">// Event Sourcing
// Gespeichert wird nicht der aktuelle Zustand, sondern die Folge aller Ereignisse. Der Zustand wird daraus berechnet.
// Start: java EventSourcing.java

import java.time.LocalDate;
import java.util.ArrayList;
import java.util.List;
import java.util.Locale;

public class EventSourcing {

    // --- Ereignisse: unveränderlich, in der Vergangenheit benannt ---
    sealed interface Ereignis permits KontoEroeffnet, Eingezahlt, Abgehoben { LocalDate datum(); }
    record KontoEroeffnet(String inhaber, LocalDate datum) implements Ereignis {}
    record Eingezahlt(long cent, LocalDate datum) implements Ereignis {}
    record Abgehoben(long cent, LocalDate datum) implements Ereignis {}

    // --- Event Store: hängt nur an, ändert und löscht nie ---
    static final class EventStore {
        private final List&lt;Ereignis&gt; log = new ArrayList&lt;&gt;();
        void anhaengen(Ereignis e) { log.add(e); }
        List&lt;Ereignis&gt; alle() { return List.copyOf(log); }
    }

    // --- Zustand: wird aus den Ereignissen berechnet ---
    record Konto(String inhaber, long saldoCent, int buchungen) {
        static final Konto LEER = new Konto(&quot;&quot;, 0, 0);

        Konto anwenden(Ereignis e) {
            return switch (e) {
                case KontoEroeffnet(String name, LocalDate d) -&gt; new Konto(name, 0, 0);
                case Eingezahlt(long c, LocalDate d)          -&gt; new Konto(inhaber, saldoCent + c, buchungen + 1);
                case Abgehoben(long c, LocalDate d)           -&gt; new Konto(inhaber, saldoCent - c, buchungen + 1);
            };
        }
        static Konto aus(List&lt;Ereignis&gt; ereignisse) {
            Konto k = LEER;
            for (Ereignis e : ereignisse) k = k.anwenden(e);
            return k;
        }
        public String toString() { return String.format(Locale.GERMANY, &quot;%s: %,.2f € nach %d Buchungen&quot;, inhaber, saldoCent / 100.0, buchungen); }
    }

    // --- Befehl: prüft gegen den aktuellen Zustand und erzeugt ein Ereignis ---
    static void hebeAb(EventStore store, long cent, LocalDate datum) {
        Konto aktuell = Konto.aus(store.alle());
        if (aktuell.saldoCent() &lt; cent) {
            System.out.println(&quot;  abgelehnt: Abhebung &quot; + cent / 100 + &quot; € am &quot; + datum + &quot;, Saldo zu niedrig&quot;);
            return;
        }
        store.anhaengen(new Abgehoben(cent, datum));
    }

    public static void main(String[] args) {
        EventStore store = new EventStore();
        store.anhaengen(new KontoEroeffnet(&quot;Sven&quot;, LocalDate.of(2026, 1, 2)));
        store.anhaengen(new Eingezahlt(100_000, LocalDate.of(2026, 1, 15)));
        store.anhaengen(new Abgehoben(30_000, LocalDate.of(2026, 3, 1)));
        store.anhaengen(new Eingezahlt(50_000, LocalDate.of(2026, 6, 30)));
        hebeAb(store, 200_000, LocalDate.of(2026, 9, 1));
        hebeAb(store, 20_000, LocalDate.of(2026, 10, 1));

        System.out.println(&quot;Gespeicherte Ereignisse:&quot;);
        store.alle().forEach(e -&gt; System.out.println(&quot;  &quot; + e));

        System.out.println(&quot;\nAktueller Zustand, berechnet aus allen Ereignissen:&quot;);
        System.out.println(&quot;  &quot; + Konto.aus(store.alle()));

        System.out.println(&quot;\nZeitreise: Wie stand das Konto am 31.03.2026?&quot;);
        List&lt;Ereignis&gt; bisMaerz = store.alle().stream().filter(e -&gt; !e.datum().isAfter(LocalDate.of(2026, 3, 31))).toList();
        System.out.println(&quot;  &quot; + Konto.aus(bisMaerz));

        System.out.println(&quot;\nNeue Auswertung aus alten Daten: Summe aller Einzahlungen&quot;);
        long einzahlungen = store.alle().stream().filter(e -&gt; e instanceof Eingezahlt).mapToLong(e -&gt; ((Eingezahlt) e).cent()).sum();
        System.out.printf(Locale.GERMANY, &quot;  %,.2f €%n&quot;, einzahlungen / 100.0);
    }

<h3>Worauf achten</h3>
<p>Die Vorteile sind eine lückenlose <strong>Historie</strong> (wichtig für Prüfungen und Fehlersuche), <strong>Zeitreisen</strong> und die Möglichkeit, aus alten Ereignissen jederzeit neue Auswertungen zu berechnen. Die Nachteile sind ebenso deutlich: Der Zustand muss berechnet werden, was bei vielen Ereignissen <em>Snapshots</em> erfordert. Ereignisformate lassen sich kaum noch ändern, weil alte Ereignisse für immer bleiben. Und Abfragen über viele Objekte („alle Konten im Minus“) sind ohne zusätzliche Lesemodelle kaum möglich. Deshalb wird Event Sourcing fast immer mit <em>CQRS</em> (Muster 35) kombiniert. Für die meisten Anwendungen ist es zu aufwendig. Es lohnt sich dort, wo die Historie selbst fachlich wichtig ist.</p>
<h3>In der Praxis</h3>
<p>Axon Framework und EventStoreDB, Kafka als Ereignisprotokoll, Buchhaltungs- und Bankensysteme. Auch Git ist im Grunde Event Sourcing: Gespeichert werden die Änderungen, der aktuelle Stand der Dateien wird daraus hergestellt.</p>

<h3>Die Idee</h3>
<p>CQRS, <em>Command Query Responsibility Segregation</em>, trennt eine Anwendung in zwei Seiten: Die <strong>Schreibseite</strong> nimmt Befehle entgegen, prüft Geschäftsregeln und ändert Daten. Die <strong>Leseseite</strong> beantwortet Abfragen aus eigenen, für genau diesen Zweck aufbereiteten <strong>Lesemodellen</strong>. Verbunden sind die beiden meist über Ereignisse: Jede Änderung auf der Schreibseite wird an die Lesemodelle weitergereicht, die sich selbst aktualisieren. Der Begriff stammt von Greg Young und baut auf dem älteren Prinzip <em>Command-Query Separation</em> von Bertrand Meyer auf.</p>
<h3>Im Code</h3>
<p>Befehle wie <code>GibBestellungAuf</code> gehen an die <code>BestellungsBefehle</code>, die den Lagerbestand prüfen und bei Erfolg ein Ereignis veröffentlichen. Zwei Lesemodelle, Umsatz pro Kunde und Bestseller, aktualisieren sich bei jedem Ereignis. Die Abfragen am Ende lesen nur fertige Werte, ohne etwas zu berechnen. Die abgelehnte Bestellung taucht in keinem Lesemodell auf.</p>
<details class="code"><summary>Java-21-Code: CQRS.java</summary><p>Direkt ausführbar mit <code>java CQRS.java</code></p><pre><code class="language-java">// CQRS (Command Query Responsibility Segregation)
// Schreiben und Lesen bekommen getrennte Modelle: eines für Befehle, eines (oder mehrere) für Abfragen.
// Start: java CQRS.java

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Locale;
import java.util.Map;
import java.util.TreeMap;
import java.util.function.Consumer;

public class CQRS {

    // ===================== Gemeinsam: Ereignisse als Brücke =====================
    record BestellungAufgegeben(long nr, String kunde, String artikel, int menge, long cent) {}

    // ===================== Schreibseite (Command) =====================
    record GibBestellungAuf(String kunde, String artikel, int menge, long einzelpreisCent) {}   // ein Befehl

    static final class BestellungsBefehle {
        private final Map&lt;String, Integer&gt; lager = new HashMap&lt;&gt;(Map.of(&quot;Buch&quot;, 10, &quot;Lampe&quot;, 2));
        private final List&lt;Consumer&lt;BestellungAufgegeben&gt;&gt; abonnenten = new ArrayList&lt;&gt;();
        private long naechsteNr = 1;

        void abonniere(Consumer&lt;BestellungAufgegeben&gt; a) { abonnenten.add(a); }

        // Befehle prüfen Regeln, ändern Zustand und liefern nichts außer Erfolg/Fehler
        void ausfuehren(GibBestellungAuf b) {
            int bestand = lager.getOrDefault(b.artikel(), 0);
            if (b.menge() &gt; bestand) throw new IllegalStateException(b.artikel() + &quot;: nur noch &quot; + bestand + &quot; auf Lager&quot;);
            lager.put(b.artikel(), bestand - b.menge());
            var e = new BestellungAufgegeben(naechsteNr++, b.kunde(), b.artikel(), b.menge(), b.menge() * b.einzelpreisCent());
            abonnenten.forEach(a -&gt; a.accept(e));
        }
    }

    // ===================== Leseseite (Query): je ein Modell pro Bildschirm =====================
    // Lesemodell 1: Umsatz pro Kunde, fertig berechnet
    static final class KundenUmsatz {
        final Map&lt;String, Long&gt; umsatz = new TreeMap&lt;&gt;();
        void aktualisiere(BestellungAufgegeben e) { umsatz.merge(e.kunde(), e.cent(), Long::sum); }
    }
    // Lesemodell 2: Bestseller-Liste
    static final class Bestseller {
        final Map&lt;String, Integer&gt; verkauft = new TreeMap&lt;&gt;();
        void aktualisiere(BestellungAufgegeben e) { verkauft.merge(e.artikel(), e.menge(), Integer::sum); }
        List&lt;String&gt; top() {
            return verkauft.entrySet().stream().sorted(Map.Entry.&lt;String, Integer&gt;comparingByValue().reversed())
                    .map(x -&gt; x.getKey() + &quot; (&quot; + x.getValue() + &quot;)&quot;).toList();
        }
    }

    public static void main(String[] args) {
        BestellungsBefehle befehle = new BestellungsBefehle();
        KundenUmsatz umsatz = new KundenUmsatz();
        Bestseller bestseller = new Bestseller();
        befehle.abonniere(umsatz::aktualisiere);               // Lesemodelle werden bei jedem Ereignis nachgeführt
        befehle.abonniere(bestseller::aktualisiere);

        List&lt;GibBestellungAuf&gt; eingang = List.of(
                new GibBestellungAuf(&quot;Sven&quot;, &quot;Buch&quot;, 2, 1_990),
                new GibBestellungAuf(&quot;Anna&quot;, &quot;Lampe&quot;, 1, 3_990),
                new GibBestellungAuf(&quot;Sven&quot;, &quot;Buch&quot;, 3, 1_990),
                new GibBestellungAuf(&quot;Ben&quot;, &quot;Lampe&quot;, 5, 3_990));

        System.out.println(&quot;Befehle (Schreibseite):&quot;);
        for (var b : eingang) {
            try { befehle.ausfuehren(b); System.out.println(&quot;  ok:        &quot; + b); }
            catch (IllegalStateException e) { System.out.println(&quot;  abgelehnt: &quot; + b + &quot; -&gt; &quot; + e.getMessage()); }
        }

        System.out.println(&quot;\nAbfragen (Leseseite), ohne jede Berechnung beim Lesen:&quot;);
        umsatz.umsatz.forEach((k, c) -&gt; System.out.printf(Locale.GERMANY, &quot;  Umsatz %-5s %7.2f €%n&quot;, k, c / 100.0));
        System.out.println(&quot;  Bestseller: &quot; + bestseller.top());
    }
}</code></pre><p><strong>Ausgabe</strong></p><pre><code>Befehle (Schreibseite):
  ok:        GibBestellungAuf[kunde=Sven, artikel=Buch, menge=2, einzelpreisCent=1990]
  ok:        GibBestellungAuf[kunde=Anna, artikel=Lampe, menge=1, einzelpreisCent=3990]
  ok:        GibBestellungAuf[kunde=Sven, artikel=Buch, menge=3, einzelpreisCent=1990]
  abgelehnt: GibBestellungAuf[kunde=Ben, artikel=Lampe, menge=5, einzelpreisCent=3990] -&gt; Lampe: nur noch 1 auf Lager

Abfragen (Leseseite), ohne jede Berechnung beim Lesen:
  Umsatz Anna    39,90 €
  Umsatz Sven    99,50 €
  Bestseller: [Buch (5), Lampe (1)]</code></pre></details>
<h3>Worauf achten</h3>
<p>Schreib- und Lesemodell haben oft völlig unterschiedliche Anforderungen. Geschrieben wird selten und mit vielen Regeln, gelesen sehr oft und in vielen verschiedenen Darstellungen. Getrennt lässt sich beides unabhängig optimieren und skalieren. Der Preis ist <strong>Komplexität</strong> und meist <strong>letztendliche Konsistenz</strong>: Laufen die Lesemodelle asynchron nach, sieht ein Benutzer seine eigene Änderung womöglich erst eine Sekunde später. Für einfache CRUD-Anwendungen ist CQRS fast immer übertrieben. Greg Young selbst betont, dass es nur für Teile eines Systems gedacht ist, nicht für das ganze.</p>
<h3>In der Praxis</h3>
<p>Axon Framework, das CQRS und Event Sourcing kombiniert, Lesemodelle in Elasticsearch neben einer relationalen Schreibdatenbank, materialisierte Sichten in Datenbanken, Projektionen in Kafka Streams. Eine einfache Form ist schon die Trennung von Methoden, die etwas ändern, und solchen, die nur lesen.</p>
