<div class="tldr">
<p>Ein <strong>Prozess</strong> ist ein laufendes Programm mit eigenem, abgeschottetem Speicher. Ein <strong>Thread</strong> ist ein Ausführungsstrang innerhalb eines Prozesses. Alle Threads eines Prozesses teilen sich denselben Speicher – das macht sie billig und schnell, aber gefährlich.</p>
<p>Greifen zwei Threads ohne Absprache auf dieselben Daten zu, entstehen <strong>Race Conditions</strong>: Ergebnisse, die mal stimmen und mal nicht. <strong>Locks</strong> verhindern das, können aber <strong>Deadlocks</strong> erzeugen. Und seit Java 21 gibt es mit <strong>virtuellen Threads</strong> eine Möglichkeit, Hunderttausende Aufgaben gleichzeitig warten zu lassen.</p>
</div>

<h2 id="prozess-thread">Prozess oder Thread?</h2>
<p>Ein Bild dafür: Ein Prozess ist eine Wohnung mit eigener Tür. Threads sind die Mitbewohner. Sie teilen sich Küche und Kühlschrank – praktisch, weil niemand etwas hin- und hertragen muss. Aber wenn zwei gleichzeitig das letzte Ei nehmen wollen, gibt es Streit. Wer etwas mit der Nachbarwohnung austauschen will, muss klingeln.</p>

<h3>Nebenläufig ist nicht parallel</h3>
<p><strong>Nebenläufig</strong> (concurrent) heißt: Mehrere Aufgaben sind gleichzeitig in Arbeit und überlappen sich zeitlich. <strong>Parallel</strong> heißt: Sie werden im selben Moment ausgeführt – dafür braucht man mehrere Kerne. Ein Koch, der zwischen drei Töpfen hin- und herspringt, arbeitet nebenläufig. Drei Köche an drei Töpfen arbeiten parallel. Die Probleme auf dieser Seite treten bei beidem auf – schon ein einziger Kern, der zwischen Threads wechselt, reicht für eine Race Condition.</p>

<h3>Die Lebensphasen eines Threads</h3>
<div class="states">
  <span>NEW</span><i>→</i><span class="run">RUNNABLE</span><i>⇄</i><span class="w">BLOCKED</span><span class="w">WAITING</span><span class="w">TIMED_WAITING</span><i>→</i><span>TERMINATED</span>
</div>
<p>So heißen die Zustände in <code>Thread.State</code>. BLOCKED bedeutet: wartet auf einen Lock. WAITING: wartet auf ein Signal, etwa bei <code>join()</code>. TIMED_WAITING: wartet mit Zeitlimit, etwa bei <code>sleep()</code>. In einem Thread-Dump mit <code>jstack</code> sieht man genau diese Zustände.</p>

<h2 id="race">Race Condition: count++ ist nicht ein Schritt</h2>
<p>In Java sieht <code>count++</code> aus wie ein Befehl. Für die CPU sind es drei: Wert aus dem Speicher <em>lesen</em>, <em>eins addieren</em>, Ergebnis <em>zurückschreiben</em>. Zwischen diesen Schritten kann der Scheduler jederzeit zu einem anderen Thread wechseln. Probier, ob du einen Zähler kaputt bekommst:</p>

<p>Das Tückische: Meistens geht es gut. Der Fehler zeigt sich nur, wenn der Wechsel genau zwischen Lesen und Schreiben fällt – im Test selten, unter Last in Produktion regelmäßig. Dieser Fehler heißt <strong>Lost Update</strong>, und er ist der Klassiker unter den Nebenläufigkeitsfehlern.</p>

<pre><code><span class="k">class</span> Zaehler {
    <span class="k">private int</span> count = <span class="s">0</span>;
    <span class="k">void</span> inc() { count++; }          <span class="c">// lesen, +1, schreiben – drei Schritte</span>
    <span class="k">int</span> get() { <span class="k">return</span> count; }
}

<span class="k">var</span> z = <span class="k">new</span> Zaehler();
Runnable job = () -&gt; { <span class="k">for</span> (<span class="k">int</span> i = <span class="s">0</span>; i &lt; <span class="s">100_000</span>; i++) z.inc(); };
Thread a = Thread.ofPlatform().start(job);
Thread b = Thread.ofPlatform().start(job);
a.join(); b.join();
System.out.println(z.get());                <span class="c">// selten 200000</span></code></pre>

<h3>Drei Reparaturen</h3>
<pre><code><span class="c">// 1. Lock: Nur ein Thread zur Zeit darf in die Methode</span>
<span class="k">synchronized void</span> inc() { count++; }

<span class="c">// 2. Atomare Operation: die CPU erledigt lesen-ändern-schreiben untrennbar (Compare-and-Swap)</span>
<span class="k">private final</span> AtomicInteger count = <span class="k">new</span> AtomicInteger();
<span class="k">void</span> inc() { count.incrementAndGet(); }

<span class="c">// 3. Bei sehr vielen schreibenden Threads: verteilte Teilzähler, erst beim Lesen summiert</span>
<span class="k">private final</span> LongAdder count = <span class="k">new</span> LongAdder();
<span class="k">void</span> inc() { count.increment(); }</code></pre>
<p>Der Bereich, den nur ein Thread zur Zeit betreten darf, heißt <strong>kritischer Abschnitt</strong>. Er sollte so klein wie möglich sein: Wer im <code>synchronized</code>-Block eine Datenbank abfragt, lässt alle anderen Threads warten.</p>

<h2 id="sichtbarkeit">Sichtbarkeit: wenn ein Thread nichts mitbekommt</h2>
<p>Es gibt einen zweiten, noch heimtückischeren Fehler. Jeder Kern hat eigene Caches, und der JIT-Compiler darf Code umstellen, solange ein einzelner Thread keinen Unterschied merkt. Ohne Absprache ist deshalb nicht garantiert, dass ein Thread die Änderung eines anderen <em>überhaupt jemals</em> sieht.</p>
<pre><code><span class="k">class</span> Arbeiter {
    <span class="k">private boolean</span> stop = <span class="k">false</span>;           <span class="c">// ohne volatile!</span>
    <span class="k">void</span> run()  { <span class="k">while</span> (!stop) { <span class="c">/* arbeiten */</span> } }
    <span class="k">void</span> halt() { stop = <span class="k">true</span>; }            <span class="c">// aus einem anderen Thread</span>
}
<span class="c">// Die Schleife kann ewig laufen: Der JIT darf stop einmal lesen und dann annehmen,</span>
<span class="c">// dass es sich nie ändert – im selben Thread wird es ja nie geschrieben.</span></code></pre>
<p>Die Lösung ist <code>volatile boolean stop</code>. Das <strong>Java Memory Model</strong> formuliert die Regel dahinter als <em>happens-before</em>: Was ein Thread vor dem Schreiben einer volatile-Variable, vor dem Verlassen eines <code>synchronized</code>-Blocks oder vor dem Ende eines Threads getan hat, sieht garantiert jeder Thread, der danach diese Variable liest, denselben Lock nimmt oder <code>join()</code> aufruft. Ohne so eine Kante gibt es keine Garantie.</p>
<div class="callout warn"><code>volatile</code> sorgt für Sichtbarkeit, nicht für Atomarität. Ein <code>volatile int count</code> mit <code>count++</code> verliert genauso Erhöhungen wie oben.</div>

<h2 id="deadlock">Deadlock: alle warten aufeinander</h2>
<p>Locks lösen Race Conditions – und schaffen ein neues Problem. Zwei Überweisungen laufen gleichzeitig: Thread 1 überweist von Konto A nach B, Thread 2 von B nach A. Jeder sperrt zuerst das Quellkonto, dann das Zielkonto. Spiel es durch:</p>

<p>Ein Deadlock braucht vier Bedingungen gleichzeitig – die <strong>Coffman-Bedingungen</strong>: Ressourcen sind exklusiv; wer etwas hält, wartet auf mehr; niemand kann einem anderen etwas wegnehmen; und das Warten bildet einen Kreis. Bricht man eine davon, ist der Deadlock unmöglich. Am einfachsten bricht man den Kreis: Alle nehmen Locks in derselben Reihenfolge.</p>
<pre><code><span class="k">void</span> ueberweise(Konto von, Konto an, <span class="k">long</span> betrag) {
    <span class="c">// Kreis brechen: immer zuerst das Konto mit der kleineren ID sperren</span>
    Konto erstes  = von.id() &lt; an.id() ? von : an;
    Konto zweites = erstes == von ? an : von;
    <span class="k">synchronized</span> (erstes) {
        <span class="k">synchronized</span> (zweites) {
            von.abbuchen(betrag);
            an.gutschreiben(betrag);
        }
    }
}</code></pre>
<p>Das berühmte Lehrbuchbild dafür sind die <strong>speisenden Philosophen</strong> von Edsger Dijkstra: Fünf Philosophen sitzen am runden Tisch, zwischen je zweien liegt eine Gabel, und jeder braucht zwei zum Essen. Nimmt jeder zuerst die linke Gabel, verhungern alle. Ein JVM-Deadlock lässt sich übrigens finden: <code>jstack</code> meldet ihn mit „Found one Java-level deadlock“. Auflösen kann die JVM ihn nicht – der Prozess muss neu gestartet werden.</p>

<h2 id="pools">Thread-Pools und virtuelle Threads</h2>
<p>Ein normaler Java-Thread – seit Java 21 <strong>Plattform-Thread</strong> genannt – ist ein echter Thread des Betriebssystems. Er ist vergleichsweise teuer: Er reserviert einen eigenen Stack (unter 64-Bit-Linux standardmäßig 1 MB Adressraum), und der Kernel muss ihn planen. Deshalb benutzt man <strong>Thread-Pools</strong>: eine feste Zahl Threads, die Aufgaben aus einer Warteschlange abarbeiten.</p>
<p>Das passt schlecht zu Servern, deren Aufgaben meistens <em>warten</em> – auf die Datenbank, auf einen anderen Dienst. Ein Thread, der wartet, belegt seinen Platz im Pool und tut nichts. <strong>Virtuelle Threads</strong> lösen das: Die JVM verwaltet sie selbst und verteilt sie auf wenige Plattform-Threads, die sogenannten Carrier. Wartet ein virtueller Thread, wird er abgehängt, und der Carrier übernimmt einen anderen.</p>

<p>Virtuelle Threads poolt man nicht – man erzeugt einfach für jede Aufgabe einen neuen. Will man begrenzen, wie viele gleichzeitig eine Datenbank treffen, nimmt man eine <code>Semaphore</code>. Ein früherer Haken ist inzwischen weg: Bis Java 23 blieb ein virtueller Thread in einem <code>synchronized</code>-Block an seinen Carrier gefesselt („Pinning“). Seit Java 24 ist das behoben.</p>

<p>Die beste Nebenläufigkeit ist die, die man nicht braucht: Unveränderliche Objekte können beliebig viele Threads gleichzeitig lesen, ganz ohne Locks.</p>

<h2 id="irrtuemer">Häufige Irrtümer</h2>
<div class="myth">
  <div><b>„Mehr Threads, mehr Tempo.“</b> – Für Rechenarbeit bringt alles über die Zahl der Kerne nichts, nur zusätzliche Wechsel. Mehr Threads helfen nur, wenn sie überwiegend warten.</div>
  <div><b>„volatile macht count++ sicher.“</b> – Es macht Änderungen sichtbar, aber nicht atomar. Dafür braucht es <code>AtomicInteger</code> oder einen Lock.</div>
  <div><b>„Ich benutze ConcurrentHashMap, also ist mein Code thread-sicher.“</b> – Jede einzelne Operation ist sicher, ihre Kombination nicht. <code>if (!map.containsKey(k)) map.put(k, v)</code> ist eine Race Condition. Richtig: <code>putIfAbsent</code>, <code>computeIfAbsent</code> oder <code>merge</code>.</div>
  <div><b>„Im Test lief es tausendmal – also ist es korrekt.“</b> – Nebenläufigkeitsfehler hängen vom Timing ab. Sie zeigen sich oft erst unter Last, auf anderer Hardware oder nach einem JVM-Update.</div>
  <div><b>„Virtuelle Threads machen alles schneller.“</b> – Sie machen Warten billig. Rechenintensiver Code wird nicht schneller, denn die Zahl der Kerne bleibt dieselbe.</div>
</div>
