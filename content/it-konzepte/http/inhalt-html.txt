<div class="erklaert">
<div class="tldr">
<p><strong>HTTP</strong> ist ein einfaches Frage-Antwort-Protokoll: Der Client schickt eine <strong>Anfrage</strong> – eine Methode wie <code>GET</code>, einen Pfad, ein paar Kopfzeilen und eventuell einen Inhalt. Der Server schickt eine <strong>Antwort</strong> – einen dreistelligen Statuscode, Kopfzeilen und meist einen Inhalt. Bis HTTP/1.1 war das alles lesbarer Text.</p>
<p>HTTP ist <strong>zustandslos</strong>: Jede Anfrage steht für sich. Anmeldungen, Warenkörbe und Sitzungen entstehen erst durch Cookies oder Tokens. Die neueren Versionen ändern nicht die Bedeutung, sondern den Transport: <strong>HTTP/2</strong> bündelt viele Anfragen auf einer Verbindung, <strong>HTTP/3</strong> läuft über QUIC statt TCP.</p>
</div>

<h2 id="aufbau">Ein Gespräch in Textform</h2>
<p>Unter der Haube von Browser, REST-Client und <code>curl</code> sieht ein Austausch in HTTP/1.1 so aus – genau so, Zeichen für Zeichen, über eine <a href="/it-konzepte/tcp-ip/">TCP-Verbindung</a>:</p>
<div class="term"><span class="c"># Anfrage</span>
<span class="m">GET</span> /api/bestellungen/42 HTTP/1.1
<span class="h">Host:</span> <span class="v">shop.example.com</span>
<span class="h">Accept:</span> <span class="v">application/json</span>
<span class="h">User-Agent:</span> <span class="v">Java-http-client/21</span>

<span class="c"># Antwort</span>
HTTP/1.1 <span class="ok">200 OK</span>
<span class="h">Content-Type:</span> <span class="v">application/json</span>
<span class="h">Content-Length:</span> <span class="v">47</span>
<span class="h">Cache-Control:</span> <span class="v">max-age=60</span>

{"id":42,"status":"versandt","summe":"59.90"}</div>
<p>Eine Zeile mit Methode, Pfad und Version, dann Kopfzeilen (<strong>Header</strong>) als <code>Name: Wert</code>, dann eine Leerzeile, dann der Inhalt (<strong>Body</strong>). Der <code>Host</code>-Header sagt, welche Website gemeint ist – so können Tausende Domains auf einem Server mit einer IP-Adresse wohnen. <code>Content-Type</code> sagt, was im Body steckt, <code>Content-Length</code>, wie lang er ist – denn TCP kennt keine Nachrichtengrenzen.</p>

<h2 id="methoden">Methoden: sicher und idempotent</h2>
<p>Die Methode sagt, was der Client vorhat. Zwei Eigenschaften sind dabei wichtiger, als sie klingen:</p>
<ul>
  <li><strong>Sicher</strong> heißt: Die Anfrage ändert nichts. Ein Crawler, ein Vorab-Laden im Browser oder ein Cache darf sie jederzeit ausführen.</li>
  <li><strong>Idempotent</strong> heißt: Zweimal ausgeführt hat dieselbe Wirkung wie einmal. Das ist entscheidend bei Netzproblemen: Kam keine Antwort, darf man eine idempotente Anfrage gefahrlos wiederholen. Ein doppeltes <code>POST</code> dagegen legt womöglich zwei Bestellungen an.</li>
</ul>
<div class="tbl-wrap">
<table>
  <thead><tr><th>Methode</th><th>Bedeutung</th><th>sicher</th><th>idempotent</th></tr></thead>
  <tbody>
    <tr><td><code>GET</code></td><td>lesen</td><td>✓</td><td>✓</td></tr>
    <tr><td><code>HEAD</code></td><td>wie GET, aber nur die Header</td><td>✓</td><td>✓</td></tr>
    <tr><td><code>POST</code></td><td>etwas Neues anlegen oder eine Aktion auslösen</td><td>–</td><td>–</td></tr>
    <tr><td><code>PUT</code></td><td>eine Ressource vollständig ersetzen oder unter bekanntem Namen anlegen</td><td>–</td><td>✓</td></tr>
    <tr><td><code>PATCH</code></td><td>eine Ressource teilweise ändern</td><td>–</td><td>nicht garantiert</td></tr>
    <tr><td><code>DELETE</code></td><td>löschen</td><td>–</td><td>✓</td></tr>
    <tr><td><code>OPTIONS</code></td><td>fragen, was erlaubt ist – etwa für CORS-Prüfungen im Browser</td><td>✓</td><td>✓</td></tr>
  </tbody>
</table>
</div>
<p>Das sind Zusagen, keine Durchsetzung: Ein Server <em>kann</em> bei <code>GET</code> etwas löschen. Er sollte es nur nie tun – sonst räumt der nächste Suchmaschinen-Crawler die Datenbank leer.</p>

<h2 id="zustand">Zustandslos: Cookies und Tokens</h2>
<p>Für den Server ist jede Anfrage eine neue Begegnung. Damit er wiedererkennt, wer fragt, muss der Client es bei jeder Anfrage mitschicken. Zwei Wege:</p>
<div class="cards">
  <div class="card"><div class="num">🍪</div><h4>Cookie</h4><p>Der Server antwortet mit <code>Set-Cookie: sitzung=a81f…</code>, der Browser schickt es bei jeder weiteren Anfrage an diese Domain automatisch mit. Wichtige Zusätze: <code>HttpOnly</code> (kein Zugriff per JavaScript), <code>Secure</code> (nur über HTTPS), <code>SameSite</code> (nicht bei Anfragen von fremden Seiten).</p></div>
  <div class="card"><div class="num">🔑</div><h4>Token</h4><p>Der Client schickt bei jeder Anfrage <code>Authorization: Bearer …</code>. Typisch für APIs und Apps. Oft ein JWT – ein signierter Datensatz, den der Server ohne Datenbankabfrage prüfen kann.</p></div>
  <div class="card"><div class="num">⇄</div><h4>Warum zustandslos gut ist</h4><p>Jeder Server kann jede Anfrage beantworten. Ein Lastverteiler kann sie beliebig verteilen, ein ausgefallener Server ist sofort ersetzbar.</p></div>
</div>

<h2 id="caching">Caching</h2>
<p>Das Schnellste ist eine Anfrage, die gar nicht erst gestellt wird. HTTP hat dafür zwei Mechanismen, beide im Baukasten oben zu sehen:</p>
<ul>
  <li><strong>Frische:</strong> <code>Cache-Control: max-age=60</code> erlaubt jedem Cache, die Antwort 60 Sekunden lang ohne Rückfrage wiederzuverwenden. Für Dateien, die sich nie ändern – etwa <code>app.3f9c2a.js</code> mit dem Inhalt im Namen –, setzt man ein Jahr.</li>
  <li><strong>Prüfung:</strong> Danach fragt der Client: „Ich habe Version <code>"v7"</code> – gibt es Neues?“ (<code>If-None-Match</code>). Ist nichts neu, antwortet der Server mit <code>304 Not Modified</code>, ganz ohne Inhalt. Das <strong>ETag</strong> ist dabei ein Versionsstempel, den der Server frei wählt, etwa eine Prüfsumme.</li>
</ul>

<h2 id="versionen">HTTP/1.1, HTTP/2, HTTP/3</h2>
<p>HTTP/1.1 von 1997 hat ein Problem: Auf einer Verbindung geht immer nur eine Anfrage zur Zeit. Browser öffnen deshalb bis zu sechs Verbindungen pro Server. <strong>HTTP/2</strong> (2015) verpackt alles in binäre Rahmen und schickt beliebig viele Anfragen gleichzeitig über eine Verbindung. <strong>HTTP/3</strong> (2022) macht dasselbe über QUIC. <h2 id="irrtuemer">Häufige Irrtümer</h2>
<div class="myth">
  <div><b>„POST ist sicherer als GET.“</b> – Ohne Verschlüsselung kann man beides mitlesen, mit HTTPS keins von beiden. Der echte Unterschied: GET-Parameter landen in Browserverlauf und Server-Logs. Passwörter gehören deshalb nie in die URL.</div>
  <div><b>„Status 200 heißt: hat geklappt.“</b> – Manche APIs antworten auch bei Fehlern mit 200 und einer Fehlermeldung im Body. Guter Stil ist das nicht, aber man muss damit rechnen.</div>
  <div><b>„PUT und POST sind austauschbar.“</b> – Der Unterschied zeigt sich bei Wiederholungen: PUT ist idempotent, POST nicht.</div>
  <div><b>„HTTPS ist ein anderes Protokoll.“</b> – Es ist dasselbe HTTP, nur durch eine TLS-Verschlüsselung getunnelt. Mehr dazu im Eintrag zu TLS.</div>
  <div><b>„HTTP/2 ist immer schneller.“</b> – Meist ja. Auf Verbindungen mit vielen Paketverlusten kann es aber schlechter sein als mehrere HTTP/1.1-Verbindungen, weil ein Verlust alle Anfragen auf der einen TCP-Verbindung aufhält.</div>
