<div class="erklaert">
<div class="tldr">
<p>Speicher kann <strong>schnell</strong>, <strong>groß</strong> oder <strong>billig</strong> sein – nie alles zugleich. Deshalb hat jeder Computer eine <strong>Speicherhierarchie</strong>: winzige, extrem schnelle Register und Caches direkt im Prozessor, darunter der größere, langsamere Arbeitsspeicher, darunter die riesige, noch langsamere SSD.</p>
<p>Das funktioniert, weil Programme <strong>Lokalität</strong> zeigen: Was gerade gebraucht wurde, wird bald wieder gebraucht, und sein Nachbar im Speicher auch. Caches laden deshalb nie einzelne Bytes, sondern ganze <strong>Cache-Lines</strong> von 64 Byte. Wer seine Daten so anordnet, dass sie nebeneinander liegen, bekommt Geschwindigkeit geschenkt.</p>
</div>

<h2 id="pyramide">Die Pyramide</h2>
<p>Stell dir vor, du arbeitest an einem Bericht. Was du gerade brauchst, liegt auf dem Schreibtisch – wenig Platz, aber sofort greifbar. Das Regal hinter dir fasst mehr, kostet aber eine Drehung. Die Bibliothek im Haus noch mehr, kostet aber einen Gang. Und das Archiv in einer anderen Stadt hat alles – aber eine Anfrage dauert Tage. Genau so ist der Speicher eines Computers organisiert. Klick auf eine Stufe:</p>

  <div class="widget-title">Von schnell und klein zu langsam und groß</div>
  <svg viewBox="0 0 600 300" id="pyrsvg" role="img" aria-label="Speicherpyramide: Register, L1, L2, L3, RAM, SSD"></svg>

<p>Warum baut man nicht einfach alles so schnell wie den L1-Cache? Zwei Gründe:</p>
<ul>
  <li><strong>Technik:</strong> Caches bestehen aus <strong>SRAM</strong> – sechs Transistoren pro Bit, schnell, aber groß und teuer. Arbeitsspeicher ist <strong>DRAM</strong> – ein Transistor und ein winziger Kondensator pro Bit, viel dichter und billiger, aber langsamer, und er muss ständig aufgefrischt werden, weil die Ladung verrinnt. Eine SSD speichert in Flash-Zellen, die auch ohne Strom ihren Zustand halten.</li>
  <li><strong>Physik:</strong> Je größer ein Speicher, desto länger die Wege. Bei 4 GHz legt ein elektrisches Signal in einem Takt nur wenige Zentimeter zurück. Der L1-Cache sitzt deshalb direkt neben dem Rechenwerk, der Arbeitsspeicher auf einem eigenen Riegel, Zentimeter entfernt.</li>
</ul>

<h2 id="lokalitaet">Lokalität: warum Caches überhaupt funktionieren</h2>
<p>Ein Cache mit 48 KB kann unmöglich die Daten eines Programms mit Gigabytes halten. Dass er trotzdem in den meisten Fällen trifft – oft in weit über 90 Prozent der Zugriffe –, liegt an zwei Eigenschaften fast aller Programme:</p>
<div class="cards">
  <div class="card"><div class="num">⟳</div><h4>Zeitliche Lokalität</h4><p>Was gerade benutzt wurde, wird bald wieder benutzt: die Schleifenvariable, der Zähler, die Methode, die immer wieder aufgerufen wird.</p></div>
  <div class="card"><div class="num">↔</div><h4>Räumliche Lokalität</h4><p>Was neben dem gerade Benutzten liegt, wird bald auch benutzt: das nächste Element im Array, die nächste Zeile im Code.</p></div>
  <div class="card"><div class="num">64</div><h4>Cache-Line</h4><p>Deshalb lädt der Cache nie ein einzelnes Byte, sondern immer einen Block von 64 Byte. Liest du ein <code>int</code>, kommen 15 Nachbarn gratis mit.</p></div>
</div>
<p>Dazu kommt der <strong>Prefetcher</strong>: Erkennt der Prozessor ein Muster – etwa, dass ein Programm Adresse für Adresse vorwärts liest –, lädt er die nächsten Cache-Lines schon, bevor sie verlangt werden. Bei einem Array funktioniert das hervorragend. Bei einer verketteten Liste nicht: Wo der nächste Knoten liegt, steht erst im aktuellen Knoten.</p>

<p>Alle vier Muster lesen dieselben 64 Werte, die Rechenarbeit ist identisch. Trotzdem liegen zwischen dem besten und dem schlechtesten Muster Welten. Das ist die wichtigste Lektion dieser Seite: <strong>Die Reihenfolge der Speicherzugriffe kann wichtiger sein als die Zahl der Rechenschritte.</strong></p>

<h2 id="mehrkern">Caches und mehrere Kerne</h2>
<p>Jeder Kern hat eigene L1- und L2-Caches. Was passiert, wenn zwei Kerne dieselbe Speicherstelle in ihren Caches haben und einer schreibt? Ein <strong>Kohärenzprotokoll</strong> sorgt dafür, dass die Kopie des anderen ungültig wird – bekannt ist etwa MESI, benannt nach den Zuständen einer Line: Modified, Exclusive, Shared, Invalid. Das kostet Zeit, und es arbeitet auf ganzen Cache-Lines.</p>
<p>Daraus entsteht eine berüchtigte Bremse, <strong>False Sharing</strong>: Zwei Threads schreiben auf zwei <em>verschiedene</em> Variablen, die zufällig in derselben Cache-Line liegen. Logisch teilen sie nichts, physisch reißen sie sich ständig gegenseitig die Line weg. Die JDK-Klasse <code>LongAdder</code> aus dem <a href="/it-konzepte/prozess-thread/">Thread-Eintrag</a> vermeidet genau das: Sie verteilt ihre Teilzähler mit Abstand auf verschiedene Cache-Lines.</p>
<pre><code><span class="k">class</span> Zaehler {
    <span class="k">volatile long</span> a;   <span class="c">// Thread 1 schreibt nur a</span>
    <span class="k">volatile long</span> b;   <span class="c">// Thread 2 schreibt nur b</span>
}   <span class="c">// a und b liegen 8 Byte auseinander – dieselbe Cache-Line, ständiges Hin und Her</span></code></pre>

<h2 id="unten">Die unteren Stufen: RAM, SSD, Netzwerk</h2>
<p>Unterhalb der Caches gilt dasselbe Prinzip, nur mit größeren Blöcken und längeren Wartezeiten. Das <a href="/it-konzepte/betriebssystem/">Betriebssystem</a> verwaltet den Arbeitsspeicher in Seiten von meist 4 KB und benutzt freien RAM als Zwischenspeicher für Dateien. Eine SSD liest ebenfalls in Blöcken; zusammenhängende Daten am Stück zu lesen, ist auch hier viel schneller als verstreute.</p>
<p>Und die Hierarchie endet nicht am Gehäuse. Eine Datenbank hält häufig benutzte Seiten im RAM, ein Server legt Ergebnisse in Redis ab, ein CDN hält Bilder in der Nähe des Nutzers, der Browser speichert Dateien lokal. Überall dieselbe Idee: Halte das Benutzte nah. Und überall dasselbe Problem: Wann ist die Kopie veraltet? Nicht umsonst gilt <em>Cache-Invalidierung</em> als eines der schwersten Probleme der Informatik.</p>

<h2 id="java">Für Entwickler übersetzt</h2>
<pre><code><span class="k">int</span>[][] m = <span class="k">new int</span>[<span class="s">4096</span>][<span class="s">4096</span>];
<span class="k">long</span> s = <span class="s">0</span>;

<span class="k">for</span> (<span class="k">int</span> r = <span class="s">0</span>; r &lt; <span class="s">4096</span>; r++)          <span class="c">// zeilenweise: Nachbarn im Speicher</span>
    <span class="k">for</span> (<span class="k">int</span> c = <span class="s">0</span>; c &lt; <span class="s">4096</span>; c++) s += m[r][c];

<span class="k">for</span> (<span class="k">int</span> c = <span class="s">0</span>; c &lt; <span class="s">4096</span>; c++)          <span class="c">// spaltenweise: jeder Zugriff eine andere Zeile</span>
    <span class="k">for</span> (<span class="k">int</span> r = <span class="s">0</span>; r &lt; <span class="s">4096</span>; r++) s += m[r][c];

<span class="c">// Gleiche Rechenarbeit, oft ein Vielfaches an Laufzeit.</span>
<span class="c">// Messen mit JMH – nicht mit System.nanoTime() um eine Schleife.</span></code></pre>

<p>Wer genau wissen will, wie ein Objekt im Speicher liegt, kann es mit dem Werkzeug JOL (Java Object Layout) aus dem OpenJDK-Projekt ausgeben lassen. Und das langfristige Ziel von Projekt Valhalla ist, dass eigene Klassen so dicht im Array liegen können wie heute nur <code>int</code> und <code>double</code>.</p>

<h2 id="irrtuemer">Häufige Irrtümer</h2>
<div class="myth">
  <div><b>„Die O-Notation sagt mir, was schneller ist.“</b> – Sie sagt, wie etwas mit der Größe wächst. Konstante Faktoren wie Cache-Fehlschläge ignoriert sie – und die können einen Faktor 100 ausmachen.</div>
  <div><b>„Mehr RAM macht den Rechner schneller.“</b> – Nur wenn er vorher auslagern musste. Sonst liegt der zusätzliche Speicher als Datei-Zwischenspeicher bereit, und das war's.</div>
  <div><b>„Eine SSD ist fast so schnell wie RAM.“</b> – Sie ist viel schneller als eine Festplatte. Aber ein Zugriff dauert immer noch etwa tausendmal länger als einer auf den Arbeitsspeicher.</div>
  <div><b>„Der JIT-Compiler optimiert das schon.“</b> – Er kann Schleifen umbauen, Werte in Registern halten und Objekte sogar ganz wegoptimieren. Aber er kann aus einer <code>LinkedList</code> kein Array machen.</div>
  <div><b>„Cache ist das, was man im Browser löscht.“</b> – Das ist einer von vielen. Prozessor-Caches arbeiten unsichtbar in Hardware; das Prinzip ist dasselbe.</div>
</div>
