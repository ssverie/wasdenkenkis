<h2 id="command-message"><span class="nr">20.</span> Command Message <span class="de">· Befehlsnachricht</span></h2>
<figure class="diagramm"><svg viewBox="0 0 660 190" role="img" aria-label="Command Message: eine Nachricht, die beim Empfänger eine Aktion auslöst" xmlns="http://www.w3.org/2000/svg"><defs><marker id="pfeil" viewBox="0 0 10 10" refX="9" refY="5" markerWidth="7" markerHeight="7" orient="auto-start-reverse"><path d="M0,0 L10,5 L0,10 z" class="head"/></marker></defs><rect x="10" y="62" width="110" height="56" rx="8" class="app"/><text x="65.0" y="95.0" class="lbl" text-anchor="middle">Shop</text><path d="M132,77.0 H506 a7,13.0 0 0 1 0,26 H132 z" class="pipe"/><ellipse cx="132" cy="90" rx="7" ry="13.0" class="pipe-end"/><rect x="306.0" y="81.0" width="26" height="18" rx="2" class="msg-a"/><path d="M306.0,81.0 L319.0,92 L332.0,81.0" class="msg-a-flap"/><line x1="515" y1="90" x2="529" y2="90" class="arr" marker-end="url(#pfeil)"/><rect x="530" y="62" width="120" height="56" rx="8" class="app"/><text x="590.0" y="95.0" class="lbl" text-anchor="middle">Lager</text><rect x="164.0" y="40" width="322" height="20" rx="10" class="tag"/><text x="325" y="54" class="tagt" text-anchor="middle">{ &quot;befehl&quot;: &quot;versende&quot;, &quot;bestellung&quot;: 4711 }</text><text x="325" y="140" class="note" text-anchor="middle">Imperativ: „Tu das!“</text><text x="590" y="140" class="note" text-anchor="middle">führt aus</text></svg><figcaption>Der Shop beauftragt das Lager per Nachricht, eine Bestellung zu versenden.</figcaption></figure>
<h3>Die Idee</h3>
<p>Eine Command Message ist ein <strong>Auftrag</strong>: Sie fordert den Empfänger auf, etwas Bestimmtes zu tun. Sie ist das Messaging-Gegenstück zu einem Methodenaufruf, nur dass der Aufrufer nicht wartet. Ihr Name ist meist ein Verb im Imperativ: <code>VersendeBestellung</code>, <code>ErstelleRechnung</code>, <code>SperreKonto</code>. Das entspricht dem Command-Muster der GoF: Ein Aufruf wird zu einem Objekt, das man verschicken und speichern kann.</p>
<h3>Beispiel</h3>
<p>Nachdem die Zahlung eingegangen ist, schickt der Shop die Nachricht <code>VersendeBestellung(4711)</code> an das Lager. Das Lager führt den Auftrag aus, sobald es dazu kommt. Ob es dafür eine Minute oder eine Stunde braucht, muss den Shop nicht kümmern.</p>
<h3>Worauf achten</h3>
<p>Ein Befehl hat einen <strong>bestimmten Empfänger</strong>, der zuständig ist, und soll genau einmal ausgeführt werden. Er gehört deshalb in einen Point-to-Point Channel. Weil Nachrichten im Fehlerfall doppelt ankommen können, sollte der Befehl so gestaltet sein, dass eine Wiederholung keinen Schaden anrichtet: Eine Bestellung, die schon versendet wurde, wird nicht ein zweites Mal verschickt.</p>
<h3>In der Praxis</h3>
<p>Aufträge an Hintergrunddienste wie „Erzeuge PDF“ oder „Sende E-Mail“, Job-Queues, die Command-Seite in CQRS-Architekturen und die Schritte einer Saga in Microservice-Abläufen.</p>

<h2 id="document-message"><span class="nr">21.</span> Document Message <span class="de">· Dokumentnachricht</span></h2>
<figure class="diagramm"><svg viewBox="0 0 660 200" role="img" aria-label="Document Message: eine Nachricht, die Daten überträgt" xmlns="http://www.w3.org/2000/svg"><defs><marker id="pfeil" viewBox="0 0 10 10" refX="9" refY="5" markerWidth="7" markerHeight="7" orient="auto-start-reverse"><path d="M0,0 L10,5 L0,10 z" class="head"/></marker></defs><rect x="10" y="62" width="110" height="56" rx="8" class="app"/><text x="65.0" y="95.0" class="lbl" text-anchor="middle">CRM</text><path d="M132,77.0 H506 a7,13.0 0 0 1 0,26 H132 z" class="pipe"/><ellipse cx="132" cy="90" rx="7" ry="13.0" class="pipe-end"/><rect x="306.0" y="81.0" width="26" height="18" rx="2" class="msg-c"/><path d="M306.0,81.0 L319.0,92 L332.0,81.0" class="msg-c-flap"/><line x1="515" y1="90" x2="529" y2="90" class="arr" marker-end="url(#pfeil)"/><rect x="530" y="62" width="120" height="56" rx="8" class="app"/><text x="590.0" y="95.0" class="lbl" text-anchor="middle">Buchhaltung</text><rect x="192.0" y="34" width="266" height="20" rx="10" class="tag"/><text x="325" y="48" class="tagt" text-anchor="middle">{ &quot;kunde&quot;: 815, &quot;name&quot;: &quot;Sven Berg&quot;,</text><rect x="195.5" y="56" width="259" height="20" rx="10" class="tag"/><text x="325" y="70" class="tagt" text-anchor="middle">&quot;adresse&quot;: &quot;Hafenstr. 7, Hamburg&quot; }</text><text x="325" y="140" class="note" text-anchor="middle">Daten, keine Anweisung</text><text x="590" y="140" class="note" text-anchor="middle">entscheidet selbst,</text><text x="590" y="156" class="note" text-anchor="middle">was es damit tut</text></svg><figcaption>Das CRM schickt der Buchhaltung die vollständigen Kundendaten. Was die Buchhaltung damit macht, ist ihre Sache.</figcaption></figure>
<h3>Die Idee</h3>
<p>Eine Document Message transportiert <strong>Daten</strong>, keine Anweisung. Der Sender liefert einen vollständigen Datensatz, etwa einen Kunden, eine Rechnung oder einen Katalog, und der Empfänger entscheidet selbst, was er damit anfängt. Der Inhalt ist das Wichtige, nicht der Zeitpunkt.</p>
<h3>Beispiel</h3>
<p>Das CRM-System verschickt die kompletten Stammdaten eines Kunden, nachdem sie geändert wurden. Die Buchhaltung speichert die neue Rechnungsadresse, das Versandsystem die neue Lieferadresse, und das Reporting zählt nur mit. Keines der Systeme muss beim CRM nachfragen, alle nötigen Daten stehen in der Nachricht.</p>
<h3>Worauf achten</h3>
<p>Document Messages sind oft größer als die anderen Arten, weil sie den vollständigen Zustand enthalten. Das macht den Empfänger unabhängig, bläht aber die Nachrichten auf. Bei sehr großen Dokumenten verschickt man besser nur einen Verweis (<em>Claim Check</em>, Gruppe 6). Die Grenze zu den anderen Arten ist fließend: Eine Antwort auf eine Anfrage ist meist eine Document Message, und viele Event Messages enthalten zusätzlich die geänderten Daten.</p>
<h3>In der Praxis</h3>
<p>Stammdatenabgleich zwischen Systemen, EDI-Nachrichten im Handel (Rechnungen, Lieferscheine), Antworten auf Abfragen und sogenannte <em>Event-Carried State Transfer</em>-Ereignisse, die den neuen Zustand gleich mitliefern.</p>

<h3>Die Idee</h3>
<p>Eine Event Message <strong>meldet ein Ereignis</strong>: Etwas ist passiert. Der Sender gibt keine Anweisung und erwartet keine Antwort. Er teilt nur mit, was geschehen ist, und überlässt es den Empfängern, ob und wie sie reagieren. Ihr Name steht deshalb in der Vergangenheit: <code>BestellungEingegangen</code>, <code>ZahlungErhalten</code>, <code>KundeUmgezogen</code>.</p>
<h3>Beispiel</h3>
<p>Der Shop meldet <code>BestellungEingegangen</code>. Das Lager reserviert die Ware, die Buchhaltung bereitet eine Rechnung vor, und der Newsletter-Dienst merkt sich das Kaufinteresse. Der Shop weiß nicht, wer zuhört. Kommt ein neuer Dienst hinzu, etwa ein Betrugserkennungssystem, abonniert er das Ereignis, und der Shop bleibt unverändert.</p>
<h3>Worauf achten</h3>
<p>Der Unterschied zwischen Command und Event ist grundlegend: Ein <strong>Command</strong> sagt „Tu das!“ und hat genau einen Empfänger, der zuständig ist. Ein <strong>Event</strong> sagt „Das ist passiert“ und hat beliebig viele oder auch gar keine Empfänger. Events gehören deshalb in einen Publish-Subscribe Channel. Bei Events gibt es zwei Stile: <em>dünne</em> Events mit nur einer ID (Empfänger müssen Details nachfragen) und <em>dicke</em> Events, die alle relevanten Daten mitliefern.</p>
<h3>In der Praxis</h3>
<p>Die Grundlage ereignisgetriebener Architekturen, Domain Events aus dem Domain-Driven Design, Event Sourcing, Kafka-Topics mit Geschäftsereignissen und Webhooks, die externe Dienste über Ereignisse informieren.</p>

<h2 id="request-reply"><span class="nr">23.</span> Request-Reply <span class="de">· Anfrage und Antwort</span></h2>
<figure class="diagramm"><svg viewBox="0 0 660 220" role="img" aria-label="Request-Reply: Anfrage und Antwort über zwei getrennte Kanäle" xmlns="http://www.w3.org/2000/svg"><defs><marker id="pfeil" viewBox="0 0 10 10" refX="9" refY="5" markerWidth="7" markerHeight="7" orient="auto-start-reverse"><path d="M0,0 L10,5 L0,10 z" class="head"/></marker></defs><rect x="10" y="70" width="110" height="80" rx="8" class="app"/><text x="65.0" y="115.0" class="lbl" text-anchor="middle">Shop</text><rect x="530" y="70" width="120" height="80" rx="8" class="app"/><text x="590.0" y="115.0" class="lbl" text-anchor="middle">Lager</text><path d="M132,75.0 H506 a7,13.0 0 0 1 0,26 H132 z" class="pipe"/><ellipse cx="132" cy="88" rx="7" ry="13.0" class="pipe-end"/><rect x="306.0" y="79.0" width="26" height="18" rx="2" class="msg-a"/><path d="M306.0,79.0 L319.0,90 L332.0,79.0" class="msg-a-flap"/><line x1="515" y1="88" x2="529" y2="88" class="arr" marker-end="url(#pfeil)"/><path d="M146,119.0 H518 a7,13.0 0 0 1 0,26 H146 z" class="pipe"/><ellipse cx="146" cy="132" rx="7" ry="13.0" class="pipe-end"/><rect x="319.0" y="123.0" width="26" height="18" rx="2" class="msg-c"/><path d="M319.0,123.0 L332.0,134 L345.0,123.0" class="msg-c-flap"/><line x1="137" y1="132" x2="121" y2="132" class="arr" marker-end="url(#pfeil)"/><text x="325" y="62" class="sub" text-anchor="middle">Anfrage-Kanal: &quot;bestand-anfragen&quot;</text><text x="325" y="168" class="sub" text-anchor="middle">Antwort-Kanal: &quot;bestand-antworten&quot;</text><rect x="222.0" y="20" width="182" height="20" rx="10" class="tag"/><text x="313" y="34" class="tagt" text-anchor="middle">Anfrage: bestand(&quot;4711&quot;)</text><rect x="265.5" y="186" width="133" height="20" rx="10" class="tag"/><text x="332" y="200" class="tagt" text-anchor="middle">Antwort: 12 Stück</text></svg><figcaption>Die Anfrage läuft über einen Kanal hin, die Antwort über einen zweiten zurück.</figcaption></figure>
<h3>Die Idee</h3>
<p>Messaging ist von Natur aus eine Einbahnstraße: Eine Nachricht geht vom Sender zum Empfänger, und damit ist der Vorgang beendet. Braucht der Sender eine Antwort, verwendet man <strong>zwei Kanäle</strong>: einen für die Anfrage und einen für die Antwort. Der Empfänger der Anfrage wird dabei zum Absender der Antwort.</p>
<h3>Beispiel</h3>
<p>Der Shop schickt eine Anfrage <code>bestand("4711")</code> in den Kanal <code>bestand-anfragen</code>. Das Lager prüft den Bestand und schickt „12 Stück“ in den Kanal <code>bestand-antworten</code>. Der Shop liest die Antwort von dort.</p>
<h3>Worauf achten</h3>
<p>Der Anfragende kann auf zwei Arten auf die Antwort warten: <strong>blockierend</strong>, indem er nach dem Senden im Antwortkanal wartet (einfach, aber dann ähnelt das Ganze stark einem direkten Aufruf), oder <strong>asynchron</strong>, indem er weiterarbeitet und die Antwort verarbeitet, sobald sie kommt. Zwei Fragen stellen sich immer: Woher weiß der Empfänger, wohin er antworten soll (<em>Return Address</em>, Muster 24)? Und welche Antwort gehört zu welcher Anfrage (<em>Correlation Identifier</em>, Muster 25)? Außerdem braucht jede Anfrage ein Zeitlimit für den Fall, dass nie eine Antwort kommt.</p>
<h3>In der Praxis</h3>
<p>Das Header-Feld <code>JMSReplyTo</code> mit temporären Antwort-Queues in JMS, das <code>reply_to</code>-Feld in RabbitMQ (das Tutorial nennt es „RPC“), <code>ReplyingKafkaTemplate</code> in Spring Kafka und <code>inOut</code>-Routen in Apache Camel.</p>

<h3>Die Idee</h3>
<p>Ein Dienst, der Anfragen beantwortet, kann viele verschiedene Auftraggeber haben. Damit er nicht fest einprogrammieren muss, wohin jede Antwort geht, schreibt der Anfragende den <strong>Antwortkanal in den Header</strong> der Anfrage, wie einen Absender auf einem Briefumschlag. Der Antwortende liest das Feld und schickt die Antwort genau dorthin.</p>
<h3>Beispiel</h3>
<p>Sowohl der Online-Shop als auch die Kassen in den Filialen fragen beim Lager den Bestand ab, beide über denselben Kanal <code>bestand-anfragen</code>. Der Shop setzt im Header <code>antwort-an: shop-antworten</code>, die Kasse <code>antwort-an: kasse-antworten</code>. Das Lager muss die beiden nicht kennen. Kommt eine App hinzu, gibt sie einfach ihren eigenen Antwortkanal an.</p>
<h3>Worauf achten</h3>
<p>Die Return Address macht den antwortenden Dienst wiederverwendbar, weil er nichts über seine Auftraggeber wissen muss. Häufig wird für jede einzelne Anfrage oder jede Instanz des Anfragenden ein eigener, temporärer Antwortkanal angelegt, der nach Erhalt der Antwort wieder verschwindet. Fehlt die Return Address, sollte der Dienst das als Fehler behandeln, statt die Antwort in einen Standardkanal zu werfen.</p>
<h3>In der Praxis</h3>
<p><code>JMSReplyTo</code> in JMS, die Eigenschaft <code>reply_to</code> in RabbitMQ (oft mit der eingebauten Direct-Reply-To-Pseudo-Queue), der Header <code>KafkaHeaders.REPLY_TOPIC</code> in Spring Kafka. Bei E-Mail erfüllt der Header <code>Reply-To</code> genau denselben Zweck.</p>

<h3>Die Idee</h3>
<p>Stellt ein System viele Anfragen hintereinander, kommen die Antworten nicht unbedingt in derselben Reihenfolge zurück. Damit der Anfragende jede Antwort richtig zuordnen kann, bekommt jede Anfrage eine <strong>eindeutige Kennung</strong>. Der Antwortende kopiert sie in seine Antwort, in ein eigenes Header-Feld, die <em>Correlation ID</em>. Wie ein Aktenzeichen, das man bei jedem Schreiben an eine Behörde angibt.</p>
<h3>Beispiel</h3>
<p>Der Shop fragt den Bestand für drei Artikel ab. Die Anfragen haben die IDs 1, 2 und 3. Das Lager beantwortet die einfache Anfrage 1 sofort, für Anfrage 3 schaut es in einem zweiten Lager nach, und Anfrage 2 dauert am längsten. Die Antworten kommen in der Reihenfolge 1, 3, 2. Über das Feld „zu“ weiß der Shop dennoch genau, welcher Bestand zu welchem Artikel gehört.</p>
<h3>Worauf achten</h3>
<p>Die Kennung muss eindeutig sein, typischerweise eine UUID. Meist verwendet man einfach die Nachrichten-ID der Anfrage als Correlation ID der Antwort. Der Anfragende muss sich offene Anfragen merken, etwa in einer Map von ID auf wartende Aufgabe, und Einträge entfernen, deren Antwort zu lange ausbleibt. Correlation IDs sind auch über Request-Reply hinaus nützlich: Wandert eine ID durch alle Nachrichten eines Geschäftsvorgangs, lässt sich der Vorgang später in den Logs aller Systeme verfolgen.</p>
<h3>In der Praxis</h3>
<p><code>JMSCorrelationID</code> in JMS, <code>correlation_id</code> in RabbitMQ, <code>KafkaHeaders.CORRELATION_ID</code> in Spring Kafka. Tracing-Systeme wie OpenTelemetry tragen nach demselben Prinzip eine Trace-ID durch alle beteiligten Dienste.</p>

<h3>Die Idee</h3>
<p>Manche Daten sind zu groß für eine einzelne Nachricht, weil Broker oft eine Größengrenze haben. Dann zerlegt der Sender sie in <strong>mehrere Teilnachrichten</strong>. Jede trägt drei Angaben im Header: eine gemeinsame <em>Sequenz-ID</em>, die alle Teile verbindet, ihre <em>Position</em> in der Folge und eine Kennung, welcher Teil der <em>letzte</em> ist. Der Empfänger sammelt die Teile und setzt sie wieder zusammen.</p>
<h3>Beispiel</h3>
<p>Der Großhändler schickt jeden Monat seinen vollständigen Produktkatalog von 30 MB an den Shop. Der Broker erlaubt höchstens 10 MB pro Nachricht. Der Katalog wird deshalb in drei Nachrichten mit der Sequenz-ID <code>K-2026-10</code> und den Positionen 1, 2 und 3 verschickt, wobei Teil 3 als letzter markiert ist. Der Shop wartet, bis alle drei da sind, und importiert dann den Katalog.</p>
<h3>Worauf achten</h3>
<p>Die Teile können in falscher Reihenfolge ankommen, einzelne können fehlen oder doppelt eintreffen. Der Empfänger muss also puffern, sortieren und nach einer Wartezeit entscheiden, was mit unvollständigen Folgen passiert. Das Sortieren übernimmt der <em>Resequencer</em>, das Zusammenfügen der <em>Aggregator</em> aus Gruppe 5. Oft ist es einfacher, die Daten abzulegen und nur einen Verweis zu verschicken (<em>Claim Check</em>, Gruppe 6).</p>
<h3>In der Praxis</h3>
<p>Die JMS-Gruppierung mit den Eigenschaften <code>JMSXGroupID</code> und <code>JMSXGroupSeq</code>, das Paar Splitter und Aggregator in Camel und Spring Integration mit den Headern <code>sequenceNumber</code> und <code>sequenceSize</code>, Multipart-Uploads bei Cloud-Speichern.</p>

<h3>Die Idee</h3>
<p>Manche Nachrichten sind nur für eine begrenzte Zeit sinnvoll. Der Sender gibt ihnen deshalb eine <strong>Ablaufzeit</strong> mit, entweder als festen Zeitpunkt oder als Lebensdauer. Ist sie überschritten, bevor die Nachricht zugestellt wurde, wird sie nicht mehr ausgeliefert. Das Messaging-System verwirft sie oder legt sie in den Dead Letter Channel.</p>
<h3>Beispiel</h3>
<p>Eine Börse verschickt Aktienkurse mit einer Gültigkeit von einer Minute. Die Kurs-App war kurz offline und meldet sich um 12:07 Uhr zurück. Der Kurs von 12:04 Uhr ist inzwischen abgelaufen und wird nicht mehr zugestellt. Die App zeigt nur aktuelle Kurse an, statt erst einen Berg veralteter Daten abzuarbeiten.</p>
<h3>Worauf achten</h3>
<p>Die Ablaufzeit schützt vor zwei Problemen: davor, dass Empfänger veraltete Informationen verarbeiten, und davor, dass sich bei einem Ausfall ein riesiger Rückstau bildet. Zeitangaben setzen voraus, dass die Uhren aller beteiligten Server ausreichend gleich gehen. Die Ablaufzeit greift nur bis zur Zustellung. Hat der Empfänger die Nachricht schon erhalten, muss er selbst prüfen, ob sie noch gültig ist.</p>
<h3>In der Praxis</h3>
<p><code>setTimeToLive()</code> bzw. das Feld <code>JMSExpiration</code> in JMS, die Eigenschaft <code>expiration</code> pro Nachricht und <code>x-message-ttl</code> pro Queue in RabbitMQ. Typische Einsatzgebiete sind Kurse, Positionsdaten, Einmalpasswörter und zeitkritische Benachrichtigungen.</p>

<h3>Die Idee</h3>
<p>Nachrichtenformate ändern sich mit der Zeit: Felder kommen hinzu, werden umbenannt oder anders aufgebaut. Damit ein Empfänger weiß, wie er eine Nachricht lesen muss, trägt sie ein <strong>Formatkennzeichen</strong>, meist eine Versionsnummer im Header. Der Empfänger liest zuerst das Kennzeichen und wählt dann den passenden Weg, den Inhalt zu verarbeiten.</p>
<h3>Beispiel</h3>
<p>Der Shop wird schrittweise auf eine neue Version umgestellt. In Version 2 hat die Bestellung zusätzlich eine Mengeneinheit, damit auch Meterware verkauft werden kann. Eine Zeit lang laufen alte und neue Shop-Server parallel. Das Lager liest das Feld <code>format</code> und verarbeitet <code>v1</code>-Nachrichten wie bisher, <code>v2</code>-Nachrichten mit Einheit.</p>
<h3>Worauf achten</h3>
<p>Das Buch nennt drei Varianten: eine <strong>Versionsnummer</strong>, einen <strong>Verweis auf eine Formatbeschreibung</strong> (etwa eine Schema-ID) oder eine <strong>Formatangabe im Dokument selbst</strong> (wie die Namespace-Angabe in XML). Ohne Kennzeichen bleibt dem Empfänger nur, das Format zu erraten. Das funktioniert, bis zwei Versionen sich zu ähnlich sind. Gut ist es außerdem, Formate möglichst abwärtskompatibel zu ändern, etwa nur optionale Felder hinzuzufügen, damit alte Empfänger neue Nachrichten trotzdem verstehen.</p>
<h3>In der Praxis</h3>
<p>Schema-IDs in der Confluent Schema Registry für Avro und Protobuf, der <code>Content-Type</code>-Header mit Versionsangabe wie <code>application/vnd.firma.bestellung.v2+json</code>, die Eigenschaft <code>type</code> in CloudEvents und Namespaces in XML.</p>
